### 1.2 ★ 报文门控机制（`sub_B41120` / `sub_B41110`，**通用，对 N8 至关重要**）

lounge 协议对象（`_proto_lounge`，ctor = **`sub_B47420`**，唯一调用者 `0xBAE0F3`）在构造时：

- `sub_B41120(this,n)`（每个 case 的**第一句**）：`if (this[n+713] == 0) → 错误码 2、返回 0`；否则若 `*(u64*)(块+16) != 0 && now > deadline` ⇒ 错误码 3。**默认（全 1 + 计时块全 0）⇒ 任意 n 一律通过**。

### 3.11 ★★★ 四条"血泪规则"（2026-09-14 真机踩出来的，适用于整个 lounge 协议）

**规则①（最贵）**：`_r` 应答**一律定长**；**变长字段混进去 = 整条静默丢弃**。
- 实测：改名应答的第 5 字段按"NUL 结尾变长名"发 ⇒ 体 **30B ≠ 46B** ⇒ 客户端**整条丢弃**
  （不报错、界面一动不动）⇒ 现象伪装成"服务端明明改了、客户端就是不认" ✗；
  改成"25B 定长（不足补 0）"后立刻正常 ✓。
- 同类：删除 **13B** / 创建 **163B** / 列表 **845B(+23n)** 全是定长（case 里都是 `push <常量>` 定长读）✓。
- ⇒ **遇到"服务端数据对了、客户端毫无反应"时，第一步先查应答体长是否等于客户端 case 里的那个常量**。

**规则②**：`del_kind` / `status` 这类 u8 **是"结果种类"**（决定客户端"接下来做什么"），
**不是请求回显、也不是成败标志**（成败看 `result`）⇒ 猜值必错，必须去反编译那个回调。

**规则③**：**势力值线上是 0 基**：`0 = 秩序(eff)` / `1 = 抵抗(zeon)`；文档与内部一律 `1 = 秩序 / 2 = 抵抗`。
- 证据：同一账号分别建"秩序/男"与"抵抗/女"两个机师，**创建包逐字节 diff** ⇒
  `off 29 : 00 vs 01`（势力）、`off 52 : 00 vs 01`（性别 = `avatar+4`，与 398B 的 +42 同源 ⇒ 交叉验证 ✓）。
- ⚠️ 线上 `1`（抵抗）**不等于**内部 `1`（秩序）—— 直接混用会把**抵抗画成秩序** ✗。

**规则④**：**`slot` 是"每阵营各自从 0 数"**。
- 证据：同一账号先在秩序建（`slot=0`）、再到抵抗建（**还是 `slot=0`**）✓。
- ⇒ 服务端存储唯一键必须是 `(账号, 阵营, slot)`；只按 `(账号, slot)` 会让**跨阵营创建互相顶掉** ✗。
- ⇒ 列表 `0xE13A` 的 `pilots_eff` / `pilots_zeon` 是**两个各 1 条的块** ⇒ 必须
  **按每个机师自己的阵营分别填**（只填"当前世界那一侧"、或只填第一条 ⇒ 另一个阵营的机师
  **永远不显示**，界面表现为"创建了但没显示" ✗ 真机实测）。

## 6. 对下游节点的影响（★ N8 关键产出）

**结论：N8 的卡点与 N7 强相关，N7 是上游。** 证据链与可执行动作：

1. **68B 体非法（必证）** ⇒ 客户端 `recv_pilot_select_r` 处理器**从未成功执行** ⇒ 客户端状态机**从未真正完成"选中机师"** ⇒ 此后它不可能按正常流程去发/应答"进频道"的报文。⇒ **N8 之前三种推送时机的实验，都是在"选择未完成"的无效状态下做的**，因此"全被拒"不能说明 0xFB85 的正确用法。 ★★ 这是本节点最重要的产出 ★★

3. **建议立刻做的服务端动作（一次只改一个变量）**：
