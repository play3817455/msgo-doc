## 0. 一句话结论

在"世界选择窗口"点确定后，客户端在**认证连接(30000)**上发 `0x3B8F`（防沉迷剩余时间查询），收到 `0x4F3F`（`u32 reset_sec`）后由该值决定**是否进入选世界流程**（`reset_sec<=0` 且有选中世界 ⇒ LoginScene FSM `state 19`；否则弹倒计时框或退回 `state 18` 重选）。

随后客户端发 `0xA380`（世界选择请求），服务器在 `0x1146` 里回 **`world_name + loungesv_host + port + userid + otp`**。该应答处理器 `sub_439030` 会在**同一个回调里主动 `sub_AF6F30()` 关掉 30000 认证连接**，并把三件套写进全局：

| 字段 | 全局偏移 | 容量 |
|---|---|---|
| loungesv 主机 | `app+1168` | 129B（拷 128） |
| loungesv 端口 | `app+1340`（u32） | — |
| **otp** | `app+1297` | 41B（拷 40） |

LoginScene FSM 走到 `state 20` 时执行 `sub_43E660`：新建步骤对象 `CGameStateStepUpdateLoginLounge`（vtable `0xD67B54`，host@`+20` / otp@`+149` / port@`+192`）并激活；该对象 `state 0` 调 `sub_AF73E0(host,port)` → `sub_AF7130` → 会话管理器 `vt[6]`，用上面三个字段去连 **30001**。

连接就绪后（`state 1→2`）发 **`0xF24B` lounge authenticate，发送体 = `u32 userid` + NUL 结尾字符串 `otp`**（不是固定 8B！见 §3.2），然后挂起在 **`state 3`**，等服务器回 **`0xA5DA`（`u32 result` + `u32 admin_lv`，8B）**。`result>=0` 才会 `state 3→4`，继续本地初始化（机师记录窗口 CPilotRecordWindow 等），最后置 `app[114201]=1` 结束该 step；FSM `state 21→22` 再关掉残留连接、进 `state 23` 挂起，等待 N8 的 `0xFB85`（频道登录应答）去连 30002。

### 2.1 LoginScene 步骤机（`vt = 0xED05CC`，tick = `sub_A88920`）

**⚠️ 对 `topics/07` 的修正**：`state 18` 的成立**不会**推进到 19，而是推进到 **23**；`state 19` 只能由 **`0x4F3F → sub_A88E90 → sub_A88430`** 这条"防沉迷应答"链路写入（或 `state 998` 兜底）。

**"卡在 18"的历史成因**（本次静态定案）：
1. 点确定后发了 `0x3B8F`，若服务器**不回 `0x4F3F`**，`sub_A88E90` 永不触发 ⇒ 永远停在 18/23；
2. 服务器回了 `0x4F3F` 但 **`reset_sec > 0`** ⇒ 只弹倒计时框，玩家不关框就停在 18；
3. `0x4F3F` 回了 `reset_sec=0` 但 `sub_43E5A0` 失败（**`app[114200]==0`：30000 认证还没成功**，或 `sub_AF6EF0()` 假）⇒ 退回 18 重选，形成"反复卡 18"。
4. 因此私服**最省事的做法**：`0x4F3F` 直接回 `reset_sec = 0`，且保证 `0x2C1A`（认证）已回成功置位 `app[114200]`。

### 2.3 `state 3` 的推进（房间认证结果）

1. 服务器在 **lounge 连接**上回 `0xA5DA`，体 = `u32 result` + `u32 admin_lv`（8B）。
2. `CGVOProtoLounge` 收包分发器 `sub_B51930` 命中 `0xA5DA` case（`cmp eax, 0A5DAh`），先 `sub_B41110(this,3)` 通过后读两个 u32。
3. 调 `esi->vt[27](result, admin_lv)` = `sub_BAAF80`：`loungeObj[33648] = (result>=0)`，转 `sub_AF75D0` → `sub_439220(app, result, admin_lv)`。
4. `sub_439220` 遍历 6 组监听器调 **`vt[7](result)`**，其中 Lounge step 的 `vt[7] = sub_430E10`：
   ```
   this[2] = result;              // 存 result
   if (result >= 0) ++this[1];    // state 3 -> 4
   else             this[1]=100;  // 失败：state=100 ⇒ default ⇒ step 结束
   ```
5. 随后 `sub_438D10(app, 4)`；`result>=0` 时 `app[350] |= 1`、`app[113950] = admin_lv`。

| recv | `0x4F3F` | 防沉迷剩余时间 | `u32 reset_sec` | 4B；`<=0` 才继续 |
| send | `0xA380` | 世界选择请求 | `u32 world_id` + `u32 频道类型` | 由 `sub_BA89B0` 发 |
| recv | `0x1146` | worldlist_select_r | `u32 result` + `str world_name` + `str loungesv_host` + `u32 port` + `u32 userid` + `str otp` | 缓冲 231B（N4 已定） |
| send | `0xF24B` | **lounge authenticate** | **`u32 userid` + NUL 串 `otp`**（长度可变） | ★N5 新结论，见下 |
| recv | `0xA5DA` | **lounge authenticate_r** | **`u32 result` + `u32 admin_lv`（8B）** | ★N5 确认 8B |

**★ `0xF24B` 发送体（`sub_B896A0` 组包，本次逐指令核对）**：

```
*(u16*)p = 0xF24B;                 // 0xF24B，2B
*(u32*)(p+2) = userid;             // u32 userid
sub_B02B40(otp, &p[6], 0x29);      // NUL 结尾字符串 otp，限长 41(含 NUL)
len = 6 + strlen(otp) + 1;
send(this, p, len);
```

⇒ 发送长度 **随 otp 长度变化**，不存在"固定 8B"。`format/README.md §2.4` 里 `u32×2（体必须 8B）` 应理解为**接收侧 `0xA5DA` 体必须 8B**（`sub_B51930` 的 0xA5DA case 连读两个 u32；4B 会读越界/校验失败）。

**★ OTP 的性质（私服可直接给空串/固定值）**：
- otp **不是**客户端计算或本地校验的东西，而是：
  1. 服务器在 `0x1146` 里下发 → 客户端存 `app+1297`；
  2. 客户端在 `0xF24B` 里 **原样回传**（`u32 userid + NUL串 otp`）；
  3. 客户端在 N8 的 `0xFB85` 里还会再拿到一次 otp 覆写 `app+1297`。
- 因此私服只要**三方一致**即可：`0x1146` 下发的 otp、`0xF24B` 回传时服务器按"NUL 串"解析、`0xFB85` 再下发同一个值。**推荐下发空串（`\0`）或固定短串**，body 变为 `u32 userid + 00`（5B）。

### 3.3 与 N3 的衔接（会话对象）

- 三个连接共用同一套建连代码：`sub_AF7130(holder, host, port)` → `dword_1201A58->vt[6](holder[0], host, port, 30000, 0)` → `sub_CA9B40`。
- `sub_CA9B40` 落点：`host → 会话+0xC4`（256B）、`port → 会话+0xA0`（u16）、`+0x98=a5(0)`、`+0x9C=0`、**`+0xB0 = a4 = 硬编码 30000`**。
- **`30000` 不是连接端口**：连接状态机 `sub_CAD510` 实际用 **`会话+0xA0`** 作端口（`sub_CB7A60(sock, *((u16*)this+0x50))`）；且三种连接（30000/30001/30002）传入的 a4 恒为 `30000`，若它是端口则 lounge 会连到 30000，与实测矛盾。⇒ **会话+0xB0（=30000）语义待定**（疑为"默认/公告端口"），**真端口 = 参数 a3 → 会话+0xA0**，与 N3 结论一致。

## 6. 对下游节点的影响

**给 N6（大厅认证与数据表下载）**：
1. **`0xF24B` 的发送体是 `u32 userid + NUL 字符串 otp`，不是固定 8B**；服务器解析必须按 NUL 串处理。`0xA5DA` 必须回 **8B**（`result` + `admin_lv`），否则客户端 `state 3` 卡死（这就是"大厅认证没回 → 卡在连接大厅"的根因）。
2. `0xA5DA.result < 0` 时客户端会 **关掉 30001 会话并把登录 FSM 打回 `state 10`（登录窗口）**，表现为"踢回登录界面"，排障时不要误判成网络问题。
3. N6 若要抓"数据表下载"，必须先把 lounge 认证打通（`state 4` 之后才会走到下载）；下载请求走的是 **lounge(30001)** 连接上的后续报文。

**给 N8（世界选择到大厅跳转 / 频道连接）**：
1. `sub_43BC70`（`0xFB85` 处理器）会**覆写同一组 `app+1168 / app+1340 / app+1297`**（即 N5 刚用过的三件套），并先 `sub_AF6FF0()` 关掉 30001 会话，再让 `sub_43ADD0` 用**同一个** `sub_AF73E0` 去连 30002 ⇒ **30001 与 30002 是同一会话槽的两次连接**，服务端需容忍"同端口槽换目标端口"。这意味着**同一进程里最多同时存在 2 条有效连接**（auth 早被 `sub_AF6F30` 关掉）。
2. 只要 `0xFB85` 不下发或 `result<0`，客户端会停在大厅 step 的 `state 11`（`app[114201]=1` 已置但不再推进），表现为"进了大厅界面但连不上下一个频道"。

**给工具/文档维护**：
- `format/README.md §2.2` 建议补一句：`sub_AF7130(holder, host, port)` 的第 4 参恒为 `30000`，**非连接端口**。
- `format/README.md §2.4` 建议把"`u32×2`（体必须 8B）"明确标注为 **接收 `0xA5DA`**，并补 `0xF24B` 发送体规格。
