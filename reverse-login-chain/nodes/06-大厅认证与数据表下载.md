## 0. 一句话结论

大厅连接（30001）上客户端跑一条 4 步链：

1. **版本交换** `0x34A9 → 0xDE24`（与 N4 同款）；
2. **大厅认证** `0xF24B`（体 = `u32 userid` + NUL 串 `otp`）→ 应答 `0xA5DA`（**体必须 8B = `u32 result` + `u32 admin_lv`**；
   少于 8B 会在分发器里 `vt[30](8)` 取满 8 字节失败而**整包丢弃**，这就是"4B 解析失败"的根因）；
3. **数据表串行下载泵**：`settings\download_list.csv`（76 行）→ 填成 `std::map<int 处理器ID, std::wstring 文件名>`
   → **每帧**若 `*(BYTE*)(泵+0x10) & 1` 就清位并取 **map 最左节点（= ID 升序）** 发 `0xF86A`（`str filepath` + `u32 hashval=0`）
   → 服务器回 `0x5290`（`u32 result | str filepath | u32 hashval | u32 src_bytes | u16 compress | u32 bin_len | bin`）
   → `sub_576160` 按 `filepath` 在 map 里**线性找到节点**，用**节点里存的 ID** 走 80 路 switch → 调该表的 vt 装载器解析 CSV 脚本
   → `sub_A4A020` 删节点 + `*(BYTE*)(泵+0x10) |= 1` → 下一帧发下一个；
4. **脚本 VM**：`sub_BBBD70`（装源码）→ `sub_AEDCF0`/`sub_AEDC30`（UTF-8 分词 + 执行）。

★ **泵只有"成功"才会推进**：`result<0`、`compress∉{0,1}`、脚本解析失败、`filepath` 匹配不上 map
—— 四种情况**都不置位、不删节点**，于是下一帧无事可做 ⇒ **泵永久卡死（无重试、无超时）**。
★ map 在每次登录时**重建**（`sub_42E9B0` → `new` + `sub_576CC0`）⇒ **每次登录都重下全部 76 张表**（完成标志不持久化）。

## 2. 状态机

### 2.1 下载泵状态机（`CDataTableDownload`）

```
状态字段： (泵+0x10) bit0 = CAN_SEND ；map._Mysize = 剩余表数

        ┌──────────────────────────────────────────────────────────┐
        │  IDLE  (bit0=0)                                          │
        │  每帧 sub_576140：bit0==0 ⇒ 直接返回（不做事）             │
        └───────────────▲──────────────────────────┬───────────────┘
                        │                          │ 初始化 / 上一张成功
                        │                          ▼
        ┌───────────────┴──────────────────────────────────────────┐
        │  SEND  (bit0 被清)                                        │
        │  sub_5760B0：map 空？ → 是 ⇒ return 0（链路结束，永不再起）│
        │                       → 否 ⇒ 取最左节点(ID 最小) → 0xF86A │
        └──────────────────────────┬───────────────────────────────┘
                                   │ 服务器回 0x5290
                                   ▼
        ┌──────────────────────────────────────────────────────────┐
        │  PARSE (sub_576160)                                       │
        │  filepath 匹配 map？ ── 否 ──► 静默返回  ┐                 │
        │         │是                              │ ★不置位不删节点  │
        │         ▼                                │   ⇒ 泵永久卡死   │
        │  sub_BBBD70 / sub_AEDCF0 成功？── 否 ────┘  (无重试/无超时) │
        │         │是                                               │
        │         ▼                                                 │
        │  switch(ID) 装载器 → sub_A4A020(删节点) → bit0 |= 1 ───────┘
        └──────────────────────────────────────────────────────────┘
```

| 状态 | 位置 | 取值 | 含义 | 进入 / 退出条件 |
|---|---|---|---|---|
| `CAN_SEND` | 泵 `+0x10` bit0 | `0` / `1` | 是否允许发下一个请求 | 进入：`sub_576160` 解析成功后 `\|= 1`；退出：`sub_576140` 先清位再 `sub_5760B0` |
| `剩余表数` | map._Mysize（泵 `+0xC`） | `0..76` | 未完成表数 | `sub_576CC0` 填满；每成功一张 `sub_A4A020` 递减；=0 ⇒ 泵静默停机 |
| 初始发送 | `sub_576CC0` 末尾 | — | **不经 bit0** 直接 `sub_5760B0` 发第 1 个 | 仅在读 CSV 成功 / 兜底插入后各调一次 |
| 兜底 | `sub_576CC0` | `{78, "msma/msma_overwrite_params.csv"}` | CSV 读失败时唯一一张表 | `sub_AEFD80` 返回 0 |

**推进条件（回答"何时请求下一个 / 何时置完成标志 / 失败是否重试"）**：

- 请求下一个：**每帧最多一个**，条件是「上一张解析成功置了 bit0」，且 map 非空。
- "完成标志"：**没有持久标志**；`map` 空 ⇒ `sub_5760B0` 直接 return 0。泵对象每次进大厅**重建**，
  所以每次登录都会把 76 张表**全部重下**（这就是"为什么每次登录都重下 76 表"）。
- 重试：**不存在**。`result<0` / `compress∉{0,1}` / 解析失败 / filepath 不匹配，四种情况都让 bit0 保持 0，
  且不删节点 —— 泵进入**永久死锁**。这是"空内容必卡"的直接原因。

**`0x5290` 逐字段核对（本节点静态复核，2026-09-14）**：

| # | 类型 | 读法（VA） | 备注 |
|---|---|---|---|
| 1 | `u32 result` | `sub_B41470`+`sub_B02DD0` @`0xB6060x` | `<0` ⇒ 整个 handler 空转（卡死） |
| 2 | `str filepath` | `sub_B02BA0(buf, cursor, 0x100)` @`0xB60640` | **NUL 结尾**，上限 256B；`memchr` 找不到 NUL ⇒ 整包丢弃 |
| 3 | `u32 hashval` | `sub_B41470`+`sub_B02DD0` @`0xB60683` | **服务端可任意填**（处理器从未读它） |
| 4 | `u32 src_bytes` | `sub_B41470`+`sub_B02DD0` @`0xB606A7` | 仅 `compress==1` 时作解压输出缓冲大小 |
| 5 | `u16 compress` | `sub_B413B0`+`sub_B02DF0` @`0xB606CB` | `0`=原样 / `1`=解压 / 其它=卡死 |
| 6 | `u32 bin_len` | `sub_B41470`+`sub_B02DD0` @`0xB606F3` | `>0x8000000` ⇒ 整包丢弃（@`0xB60711`） |

## 6. 对下游节点的影响

- **本节点结论如何支撑 N7**：N7（机师列表/创建/选择）依赖大厅初始化时**已注入的 76 张表**。
  若泵卡死（§2.1 四种情况），`CPilotRecordWindow`（lounge step case 6）拿不到表数据，
  `0x60CD`/`0xFD3E`/`0xF705` 的字段就填不出来 —— 排障时应**先看泵是否停在某个 filepath**。
- **服务端实现要点**：
  1. `0x5290` 的 `result` 必须 `>= 0`、`compress` 必须为 `0`（最省事）、`filepath` 必须与客户端请求**逐字节相同**；
  2. `bin_len` 必须 > 0，且**每个 case 结束时游标必须正好在报文尾**（多发 1 字节都会被丢）；
  3. `hashval` 随便填（不校验）；`bin_len ≤ 0x8000000`；
  4. 76 张表**必须逐张按序应答**，一张失败就永久卡住（客户端**不重试**）。
- **卡点/风险**：
  - ⚠️ 表内容必须是**合法 UTF-8 且非空**，否则 `sub_AEDC30` 返回 0 ⇒ 卡死（第 6 条的实证）。
  - ⚠️ CSV 方言（`formats\README.md` §四）必须遵守，否则行回调把表头当数据、或 `JAPAN` 行被丢。
