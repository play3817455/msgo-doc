## 0 一句话结论

大厅/认证连接（30000/30001/30002）在 TCP 之上跑 **iVCE 传输层**：先做一段**裸字节**密钥交换
（C→S 16B = 客户端 RSA 模数 `n_C` 小端；S→C 32B = **两段都用 `n_C` 做 RSA 加密的 16B 会话密钥**），
客户端用自己私钥解出两把 16B 密钥，分别装进 **入站解密 ctx(+0x3A0)** / **出站加密 ctx(+0x290)**，
之后全部流量用**自研 Camellia-128 变体（counter 打在第 1 个白化子密钥上）**按块加密，
帧头是 **4B 小端"明文长度"**（等价于"块数<<4 | 尾字节数"）。
⇒ **服务端只需 `pow(K, 65537, int(首包,'little'))` 做公钥加密，无需知道客户端私钥** ——
`server/camellia128.py` + `server/access_sticky.py` 的做法在原理上正确，但**"block2 原样发"是 bug**
（见 §4.3/§5.1）。

### 3.3 加密层帧格式（★ 修正旧结论）

**发送（`sub_C882F0`）**：

```
1) 取待发明文长度 n = this[304]-this[303]（发送环）
2) 单次上限 clamp = max(this[114]-18, 1400)，this[114] = 0x4000 = 16384  ⇒ 上限 16366B
3) full = n >> 4，tail = n & 0xF
   需要空间 = 4 + 16*full + (tail ? 16 : 0)         // 尾块不足 16B 也发一整块
4) ★写 4B 头：LE u32 = n —— 即「明文长度」；数值上恒等于 (full<<4)|tail
5) full 个整块：sub_CB4970(128, in, this+164 /*+0x290*/, out)；每块后 ++this[164]；sub_CAC660(out,16)
6) 尾块：前 tail 字节取原文，其余用 sub_CB09E0(sub_CAC640(this[19])) **随机填充**；
   同样加密（同一计数器递增）并写出 16B
7) this[303] += n；若发送环读完（this[304]==this[303]）双指针归零
```

**接收（`sub_C88510`）**：

```
1) 取解密输入环；可读 < 4 直接返回 1（等更多）
2) n = 环首 u32；若 n == 0 或 n > sub_C87F30(this)(=16366) ⇒ 错误 (13,5) 关连接
3) full = n >> 4，tail = n & 0xF，帧长 = 4 + 16*full + (tail?16:0)；不足 ⇒ 返回 1
4) 输出环余量检查（this[315]+X-this[316] < n）⇒ 错误 (10,3)
5) full 个整块：sub_CB4AD0(128, in, this+232 /*+0x3A0*/, out)；每块 ++this[232]；明文入环
6) 尾块：同理解密，只取前 tail 字节
7) 消费整帧，继续下一帧
```

**★ 铁律**：
1. **4B 头是明文**、且**数值 = 明文长度 n**（老文档写"(块数<<4)|尾字节数"是等价表述，但**必须按 n 写**：`full=n>>4, tail=n&0xF`）；
2. **尾块也占一整块 16B 密文**（`need = 16*full + (tail?20:4)`）；
3. **计数器 = ctx 第 1 个 dword**（`+0x290` 出站 / `+0x3A0` 入站），密钥扩展 `sub_CB4580` 会把该 dword 写成 `KL[0]`，
   之后**每加/解密一块 `++` 一次、跨消息跨连接持续累加、代码里无任何复位点** ⇒ 语义 = `KL[0] + 该方向累计块数 (mod 2^32)`；
4. **单帧明文 ≤ 16366B**（= 0x4000 − 18）；**超了客户端不会"只丢这一帧"，而是 `sub_CAC820(13,5)` 直接关连接** ✗
   （`sub_C88510`：读 4B 头 `v4`；`if (v4 > sub_C87F30(this) || !v4) break;` ⇒ 走到函数尾 ⇒ 报错关连接）；
5. ★★ **超过 16366B 的报文必须切成多帧连发**（服务端义务）：同一函数 `sub_C88510` 在 `sub_CAC6D0(帧长)`
   消费掉一帧后会**循环读下一帧** ⇒ 连续多帧会被同一次调用全部消费 ⇒ **应用层报文可以跨帧** ✓。
   2026-09-14 实测（多帧连发后）：129401B 表 = 8 帧、51725B 选机师体 = 4 帧（线上 51760B），
   客户端全部接受并继续交互 ✓ —— 这正是历史上"选机师就断链 / 大表一过就掉线"的唯一根因。
6. 握手阶段（16B / 32B）是**裸字节流，没有 4B 头**；从加密阶段开始才带 4B 头。

### 3.4 握手报文序列（Mode A，= 线上实测形状 ✅）

```
C→S : 16B  客户端 RSA 模数 n_C（小端；实现上取 ctx vt[4] 导出的 16B）
S→C : 32B  block1(16B) ‖ block2(16B)
           block1 = RSA_enc(K_in , n_C)  → 客户端解密后装入 +0x3A0（入站解密）
           block2 = RSA_enc(K_out, n_C)  → 客户端解密后装入 +0x290（出站加密）
之后 : 全部帧 = 4B LE 长度头 + 16B×N 密文（Camellia-128 变体 + 计数器）
```

RSA 细节：`sub_CA2F20(bitlen=128)` ctor 置 `bits=128, e=65537`；
`sub_CA2F90(holder,128)` = 建 ctx + **生成本端密钥对**（随机源 = `holder[1]`）；
`vt[4] = sub_C8F9C0` 导出模数、`vt[5] = sub_C8FA00` 装入 16B 模数、
`vt[2] = sub_C9D2F0` / `vt[3] = sub_C9D330` 为两个方向的模幂（发送侧/接收侧）。
⇒ 本节点实测：**密文/模数/明文全按小端解释**（与 `server/_rsa2.py` 穷举一致）。

### 3.5 Camellia 身份确认 ✅

- `sub_CB4580` = 密钥扩展（128bit → 26×64bit = 52 dword 子密钥）；`sub_CB4970/sub_CB4AD0` = 加/解密一块；
  `sub_CB4450` = 2 轮 F 函数。
- `server/camellia128.py` 自检用**官方向量** `key=0123..3210 → ct=67673138549669730857065648eabe43`
  且 `KA=ae71c3d55ba6bf1d` **通过** ⇒ **它就是标准 Camellia-128**（该文件头部"不能与标准 Camellia 互操作"
  的注释是**过时/自相矛盾**的，应以 selftest 为准 ⚠️）；
- 唯一非标准之处：**counter 加到第 1 个白化 dword**（`camellia128.encrypt_block` 的 `w[0] += counter`）。

## 5 待研究（交 N4 及后续）

1. **⚠️ block2 是否 RSA（本节点最高优先级的悬案）**：静态证据说"是"（`sub_CA11D0` 两次 `sub_C9F820`），
   `access_sticky` 的 `STICKY_REPLY2` 实验说"不是"。**判定实验**：HW bp `0x00CB4580`，
   第 1 次/第 2 次命中时 dump 入参 16B，与线上发的 `block1/block2` 比对：
   - 若 `命中值 == block_n` ⇒ 原样使用；
   - 若 `命中值 == pow(block_n, d, n_C)`（= 无法预测的伪随机） ⇒ 走了 RSA 解密（应当如此）。
   同时把 `_rsa2.py` 的穷举改成"对 block2 也做 `pow(x,E,n_C)` 关系验证"。
2. **`+0x280` 初值 1 的写入点未定位**（立即数扫描只找到 `sub_CA31E0` 的"写 2"）。
   反推初值必为 1；建议用写断点 `[session+0x280]` 在真实建连时抓一次写入者。
3. **tick 调用顺序**：`sub_C9E810`（1/2/6）与 `sub_CA3030`（3/4/5）谁先谁后、由哪个虚槽成对驱动，尚未坐实。
4. **握手阶段是否有 type1/2 时间戳帧**：`sub_CAD400` 会主动**合成** type3(5B)/type2(9B) 喂给本端解析器；

5. **孪生实现用途**：`sub_CA3250` + `sub_C88910` + `sub_CB6350`（另一种分组算法、无计数器）是什么场景
   （可能是 iVCE 的"非加密/其他算法"档）—— 若真实客户端可能切到该档，需先确认选择条件。
6. `sub_C9C9D0`/`sub_CAC640`/`sub_CB09E0` 的随机数源（尾块填充与 Mode B 密钥生成共用）——影响"是否可预测"。
