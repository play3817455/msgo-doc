## 0. 一句话结论

1. **30002 不是新协议**：它就是**同一个 `_proto_lounge_client` 协议对象**（holder `dword_1201A60+0x20B0`）
   的**第二次连接**，因此**完全复用 N3 的 access 握手 + Camellia-128(counter) 帧层**，
   并且**复用同一个 recv 分发器 `sub_B51930`**（30001 与 30002 的报文 ID 空间是同一套）。
   ⇒ 服务端**不需要**为 30002 写新的解密/握手代码，"最小可用频道服"= 同一套壳 + 新增首屏应答分支。
2. 连上 30002 后，客户端由每帧状态机 **`sub_43ADD0`（状态 = `app[+1396]`，值 2..21）** 驱动：
   - `case3` 等会话就绪 → `case4` `sub_AF73E0(host,port)` 建连 → `case5` 发 **`0xF24B`**（lounge authenticate）
     → `case6` `app[114201]=1`（"大厅就绪"标志）→ `case7..21` **首屏初始化爆发**（见 §2.2）。

3. ★**但本轮实跑证明 30002 这一段根本走不到**：客户端在 30001 上回完 `0x063E` 后**立刻断开 30001 并退回"选择战区"界面**，

### 3.6 ★★★★ 首屏各应答的**体格式**：一律"按 case 的读取序列定长"（已解 3 条）

**方法（可复用，一次成型）**：`recv_<名>_r` 日志串 → `xrefs_to` 取它在 `sub_B51930` 里的引用点（必落在该 case 的解析区）
→ 反汇编该点**往前 ~0x200** 就是"字段读取序列"（`sub_B02DD0`=u32、`sub_B02DF0`/`sub_B413B0`=u16、`sub_B02BA0`=NUL 串、
`sub_B41470`=取槽指针、`sub_B416C0`/`sub_B05E40`/`sub_B41850`=向量构造、`sub_B434F0`=逐元素读）
→ 末尾必是 `cmp <cursor>, <end>` = **"游标恰到底"** ⇒ **体长必须精确匹配** ✗ 多一字节少一字节都会失败。
**ID 双重验证**：在 `sub_B51930` 里搜 `cmp eax, <ID>`（`insn_query {mnem:"cmp", op1:<十进制ID>, func:"sub_B51930"}`）
⇒ 命中点应在该 case 之前 ✓。

**★ 读取器宽度速查（必须反编译确认，别按"看起来"猜 ✗）**：

| 函数 | 宽度 | 反编译实证 |
