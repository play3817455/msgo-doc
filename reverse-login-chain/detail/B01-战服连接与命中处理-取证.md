# B01 · 战服（battle）连接方式 + 命中/伤害客户端处理链（取证）

> 2026-09-15，IDA 实测（`unpacked\GundamOnline_CHINA_v15.exe.i64`，基址 0x400000）。
> 目的：回答两件事 —— **① 战斗连接怎么建（TCP/UDP、几个连接）**；**② 服务器回的伤害在客户端怎么用**。

---

## 一、客户端在启动时创建 **3 个 VCE 会话对象**（`sub_AF6CB0`）

`sub_AF6CB0`（VCE 管理器初始化，只跑一次）：

| 全局 | 类 | 构造器 | vtable 基址 | 会话字段偏移 |
|---|---|---|---|---|
| `dword_1201A5C` | `CGVOProtoAuth` | `sub_BA8BB0` | `0xEED714` | `+968` |
| `dword_1201A60` | `CGVOProtoLounge` | `sub_BAE0F0` | `0xEEDB6C` | `+33640` |
| **`dword_1201A64`** | **`CGVOProtoBattle`** | **`sub_BAAE90`** | **`0xEED7AC`** | **`+16576`** |

```c
dword_1201A58 = sub_CA9250(0, 1, off_110F16C);          // VCE 管理器
mgr->vt[132](50);  mgr->vt[136](15000);                 // 会话数/超时设置
dword_1201A5C = sub_BA8BB0(sub_BDC300(984));            // auth
dword_1201A60 = sub_BAE0F0(sub_BDC300(33656));          // lounge
dword_1201A64 = sub_BAAE90(sub_BDC300(16592));          // ★ battle
sub_C7F510(300000, 0);   // ×3（三个会话各设 300s）
```
⇒ **战斗协议对象从启动就在，战斗中只是用它建"第 3 条连接"** ⇒ 结构上**同一时刻只有一条战斗连接**（P2P 需要 N 条 ⇐ 排除）。

★**vtable 基址更正**：`CGVOProtoBattle` 基址 = **`0xEED7AC`**（我之前写 `0xEED7A8` 是把 vtable 前面的 RTTI 指针当成了槽位，偏了 4 字节）。
自检：`0xEED7AC + 0x54 = 0xEED800` = **收包分发器 `sub_B0CC20`** ⇒ 与 lounge（`0xEEDB6C+0x54=sub_B51930`）/auth（`0xEED714+0x54=sub_B03D30`）**同一套槽位布局**。
⇒ 由此 `vt+0x1F8 = 0xEED9A4 = sub_BA9F80`（**15 参数** handler，见 §三），`vt+0x178` 为 `entity_msma_show_hp` 用。

## 二、三条连接的建立方式**完全相同**（⇒ 传输层没有差异）

连接包装函数（都只在**一个**调用点被调）：

| 包装 | 目标会话 | host / port 来源 | 调用者 |
|---|---|---|---|
| `sub_AF73B0` | auth（`[1201A5C+968]`） | `sub_A2A1B0()` / `sub_A2A1D0()` | `sub_43A480`（FSM） |
| `sub_AF73E0` | lounge | 步骤对象的 `+20` / `+192` | `sub_43ADD0`(FSM) / `sub_43BAC0`(大厅 step) |
| **`sub_AF7400`** | **battle（`[1201A64+16576]`）** | 步骤对象 `+20` / `+192` | **`sub_440080`（`CGameStateStepUpdateLoginBattle` 的 tick）** |

三者都落到**同一个**底层 helper：

```c
// sub_AF7130(sessionField, host, port)
v4 = *(_DWORD*)this;                                  // VCE 会话句柄
if ( (*(vt+16))(v4) != 5 && (*(vt+16))(v4) ) (*(vt+16))(v4);   // 状态检查
return (*(mgr->vt[24]))( dword_1201A58, *(_DWORD*)this, a2 /*host*/, a3 /*port*/,
                         30000 /*ms 超时*/, 0 /*flag*/ );
```
⇒ **auth / lounge / battle 三条连接用的是同一 API、同一套参数（含那个 `0` 标志）**；
⇒ 游戏侧**没有任何"用 UDP"或"协商传输层"的代码**。

**战斗连接调用链（完整）**：
```
lounge: 0x5383 recv_btlroom_enter_r (battlesv_host/port/otp/room_id)
  → sub_AF8180 → sub_450E10(app,…)   置 app+115060(host)/+115232(port)/+115189(otp)、mode=2
      → sub_442970 → 演出204 通过 → sub_43F780 建 CGameStateStepUpdateLoginBattle
          （ctor: host→+20(cap129)、otp→+149(cap41)、port→+192、a5→+196、a6→+200；vtable 0xD68474）
      → 该 step 的 tick = sub_440080：
          state0: sub_AF7400(a1+20, *(u16*)(a1+192))   ← ★真正发起连接
          state1/2: sub_BAADC0(…, a1+149 otp, …)        ← 发 0xF24B authenticate
```
**实测印证（本机私服）**：客户端真的按 `0x5383` 给的 host/port **主动新连**（30002）→ `0x34A9 proto_version_check` → `0xF24B`（**battle 变体 len=21**，比首屏的 23 少/多 2B）→ `0xA5DA` 全部跑通 ✓。

**传输层结论**：
- **TCP 起步即可**（客户端不会因为对方不是 UDP 而拒绝——它是**主动 connect**，且我们的纯 TCP 服务端已经走完握手）。
- SDK（iVCE）内部**具备 UDP 会话能力**（`VCE_LOG_TYPE_SESSION_UDP_SYN/SYNACK/SYNACKACK`、`…_UNRELIABLE_DATA`、分片、`STREAM_MULTIPLEXER` 一连接多逻辑流），但**游戏侧不指定传输层**；是否升 UDP 由 SDK/管理器的默认行为决定 ⇒ **实现顺序建议：先 TCP 打通战斗，再观察客户端是否发起 UDP（若有，再补 UDP 会话层）**。

## 三、服务器回传的伤害在客户端怎么用（"服务端算完回传"的客户端侧实证）

`recv_weapon_hit_from`(0x49C6, **43B**) 的 handler：
```
vt[0x1F8] = sub_BA9F80 (15 参数) → sub_AFBE80(ent_id, from_ent_id, weapon_itemid, charge_lv,
        hp_now, hp_max, damage, spbits, hit_pos_x/y/z, hit_dir, body_region, optbits, shield_hp_now)
   ├─ weapon_itemid != 0 ⇒ sub_4BC950(...)      // 追加载具/武器上下文版本
   └─ 否则                ⇒ sub_4B6990(...)
   └─ sub_541450(ent_id, from_ent_id, weapon_itemid, damage, hit_pos_x/y/z)  ★用包里的 damage
```

**(a) `sub_4BC950` —— HP 与"掉血量"完全由服务器数据推导**：
```c
sub_4B59B0(&ent, from_ent_id);                            // 按 id 解析实体
if ( a6 && a7 ) v59 = sub_CC6400((double)a6 / (double)a7 * flt_D69A58);  // ★hp_now/hp_max → HP 百分比
v71 = sub_475410(*v15) - a6;                              // ★"掉血" = 本地旧 HP − 服务器给的 hp_now
...
v73 = a6;  v74 = a7;  v75 = a15;                          // hp_now / hp_max / shield_hp_now 进结构
sub_489890(&v69);                                         // 更新实体/血条/UI
if ( 实体是自己(flag&1) && 掉血>0 ) sub_43FC00(app);        // 受击表现（屏幕效果/DamageFilter）
```
⇒ 客户端**不做攻防公式**，它只是拿 `hp_now/hp_max` 算血条、拿"旧HP−新HP"算掉血。

**(b) `sub_541450` —— 伤害数字直接用包里的 `damage`**：
```c
sub_540B60(&v20, ent_id);  sub_4B59B0(&a1, from_ent_id);
v21 = a4;                     // ★ packet.damage
v22[0..2] = (float)hit_pos_x/y/z;   sub_4624C0(v22);
v11 = sub_5409E0(0.0, …, &v21);     // 造"伤害数字/命中"对象（带 damage + 世界坐标）
(*(vt+128))(obj, v11);              // 交给 UI/世界管理器显示
```
⇒ **屏幕上的伤害数字 = 服务器报文里的 `damage` 字段** ✓✓（不是本地算的）。

⇒ 与协议侧证据（客户端上报 `send_weapon_hit_to` 无任何伤害/HP 字段）合并：**伤害全链路都是"服务器算 → 客户端显示"**。

## 四、对本项目（Go 战服）的直接结论

1. 战服**用 TCP + 现有 iVCE 帧层 + 握手**起步（auth/lounge 那套代码可直接复用第三条会话）。
2. 战斗连接是**第 3 条 VCE 会话**（客户端固定 3 个协议对象）⇒ 服务端只需为每个客户端提供 **1 条**战斗连接（不需要 N 个 peer 连接）。
3. 服务端必须**自算伤害**并下发 `recv_weapon_hit_from`（43B）等；客户端会：
   - 用 `hp_now/hp_max` 刷血条（`sub_4BC950`），
   - 用 `damage` + `hit_pos` 弹伤害数字（`sub_541450`），
   - 用 `shield_hp_now/spbits/optbits` 做护盾与状态表现。
4. 待办：UDP 观察（战斗中是否出现 SDK 的 UDP 会话）；`0x5383` 之后 battle 首屏需要哪些 S→C（`0xDE24/0xA5DA` 已知）。
