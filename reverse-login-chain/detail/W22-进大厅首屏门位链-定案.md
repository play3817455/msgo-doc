## §8 可复用方法（本轮沉淀 ✓）

1. **门位反查法（新武器 ✓✓✓）**：`find_bytes "78 05 00 00"` 列出所有 `app+0x578` 访问点 ⇒
   其中 `83/81/80 8X/89 …`（`or`）就是**置位点**，读出立即数 ⇒ 位号；再由 `xrefs_to <thunk>` 得到
   vtable 槽地址 ⇒ `槽地址 − 0xEEDB6C` = `OFF` ⇒ 用它去**所有 recv case 体里搜 `8B 8X <OFF>`** ⇒
   即得"哪条回包置哪个位" ✓（一次 `py_eval` 出 350 条全表）。
2. **"应用处理器"识别法**：case 体末尾 `mov edx,[esi]; mov edx,[edx+OFF]; …; mov ecx,esi; call edx`。
   ⚠️ 中间可能插一条别的 `mov`（如 0x0906 的 `mov eax,[esp+…]`）⇒ **不能只搜相邻字节**，要按指令解码。
3. **数体长只数"线体游标"那一侧**（`&var_2C44`），内存 walker（`&var_2C3C`）不算 ✓。
4. **判"是否被接受"必须先确认该格是否门控**：非门控格上的"下一条请求出现"是**假阳性** ✗。
5. 用 `py_eval` 在 IDA 里做批处理（`bisect` + 字节扫描）比逐条 `disasm` 快一个数量级 ✓。
6. ★★**字段名挖掘法（本轮最强武器 ✓✓✓）**：客户端每条 case 体里都有
   `sub_41D990(logobj, "field_name=")` 形式的打印 ⇒ **`push offset <串>` 的串就是字段名**，
   而且**打印顺序 = 读取顺序** ⇒ 用 `py_eval` 枚举 case 范围内的 `push`/`mov` 的 `o_imm` 操作数、
   `get_strlit_contents` 取串，即可把**整条报文的字段名按序全列出来**（比猜字段快 10 倍 ✓）。
   更细一层：元素打印器（如 `sub_B4A7E0`/`sub_B49DE0`/`sub_B4A970`）会打印元素内**每个字段**，
   连 `struct` 偏移都能反推出来（`a2[14]`/`*(u16*)(a2+8)` 之类直接给出偏移 ✓）。

### 13.7.1 "无应答"是误读：回包是流程的一部分

§13.6 把 `0x3F68`/`0x7A29` 当"只落库、不回包"处理，结果是**界面不动**。
原因在 `sub_42A610` 的入参检查上（§13.6.1 抄录的那段）：它只在 `[app+1BE1F] != 0` 时
才应用下发的 step，而 `[app+1BE1F]` **只有发过上报才会被置 1**（`sub_42A4B0`/`sub_42A490`）：

```

sub_42A490（发 0x3F68）：AFE8E0 → B8AFF0 之后  同上
sub_42A610（应用下发）：0x42A621  cmp dword ptr [app+1BE1Fh], 0 → 是 0 就走"忽略"
                          0x42A649  mov [app+1BE1Fh], 0            ; 应用完清闩
sub_A8AF30 case 0 @0xA8AF86 也读同一个闩（闩立着 ⇒ 状态机不推进主菜单）
```

⇒ 服务端不回包 = 闩永远立着 = **客户端的 step 永不更新**（`app+0x1BDF4` 停在旧值）、
C++ 侧的状态机也不再推进；界面自然"没刷新"。修法：这两条上报回一份 `0x1A39`
（体与 `0x3128` 的应答完全一致，`pushTutoState()`）。

### 14.2 命令形状与触发点

### 14.3 ★体长必须是 4（客户端"游标恰到底"校验）

处理块 `0xB6F1D1`..`0xB6F33A`：读 `u32 result`（`sub_B02DD0`，带边界检查）之后，
`0xB6F24A: cmp ebx,[var_2C40]` —— `ebx` 是**读之后的游标**、`[var_2C40]` 是**体末**，
不等就走 `push 1 / push 19h`（**门 25 失败**）：

```asm
00B6F246  mov  ebx, [esp+2C5Ch+var_2C44]   ; 读之后的游标
00B6F24A  cmp  ebx, [esp+2C5Ch+var_2C40]   ; == 体末 ?
00B6F24E  jnz  short loc_B6F22F            ; 不等 ⇒ push 1 / push 19h（门 25 失败）
...
00B6F313  mov  edx, [esi]; mov edx, [edx+9Ch]
00B6F31B  push ecx                          ; arg = result
00B6F31E  call edx                          ; 交给业务层（vt[0x9C]）
```

| 回的体长 | 游标 | 结果 |
|---|---|---|
| 8B ✗ | `+4` ≠ 体末 `+8` | 门 25 失败 ⇒ 判定"退出失败" ⇒ **退不出来** |
| **4B ✓** | `+4` == 体末 | 正常回到选择机师页 |

辨识特征（旧档原话）：**不是白屏、而是"退不出来"、游戏内还能操作**。
旧服务端把体从 8 改回 4 之后用户实测「解决了。可以返回了。」
（`server/docs/MEMORY.md` P193 → P195 → P196，含 x64dbg 硬件断点 `0xB6F24A` 现场）。
本仓 `gen.SC0xa00fLoungePilotExitRFixedBodySize == 4` ✓ 与实测一致，另加断言钉住防回归。

- **在线簿摘掉**：成员列表 `0x1D02` 读在线簿，不退的话"退出去换个机师再进"会看到两个自己。

  ⇒ 不清的话新机师吃不到 `0xB080`（白屏）与军衔组。`ChannelID` 不动。

## §15 定案（2026-09-22 第四轮）：`0xBD2D` 断链 / `tuto_flags` 是什么 / `0x7A29` 的两条路 / 建号势力闸门

### 15.1 ★事故：一次活动位上报把整条会话踢了（`0xBD2D` 少剥 2B opcode）

用户日志：

```
2026/09/22 13:41:47 [channel] session ended: codec: 报文体未消费完：游标 8 / 总长 10
2026/09/22 13:41:47 [lounge] presence leave pilot=6 channels=1
```

**不是客户端的问题**。`codec.Reader.Finished()`（`internal/wire/codec/cursor.go`）做的是
「游标 == 报文末尾」校验，报"游标 8 / 总长 10"= 解出来用了 8B、可体里还有 2B。

那 2B 就是 **opcode**：连接层交给 handler 的是**整条负载**（`2B opcode + body`，见
`conn.Registry.Handle` 的注释），同包 handler 一律 `conn.Body(payload)` 自己剥，
而 `lounge/evflag3.go` 的 `onPilotEvflag3Set` 当时直接拿 `payload` 去解 8B 掩码：

```go
gen.DecodeCS0xbd2dLoungePilotEvflag3SetBody(payload)   // ✗ 多了 2B opcode
if err != nil { return err }                            // ✗ 再抛回 ReadLoop ⇒ 断链
```

- `2B opcode + 8B 掩码` 恰好先解出 8B ⇒ `Finished()` 报错（10B 的体）；
- `Registry.Handle` 把 handler 的 error 上抛给 `ReadLoop` ⇒ **会话结束**，连带在线簿 leave。

两条口径（写进本仓规范，别再犯）：

1. **handler 一律 `conn.Body(payload)`**；
2. **`fire-and-forget` 的上报（无应答命令）解码失败只能记日志、绝不 `return err`** ——
   丢一次活动位/引导位不该断链。

落地：`lounge/evflag3.go`（剥 opcode + 吃掉解码错误）、
`lounge/evflag3_test.go:TestEvflag3SetHandlerNeverBreaksSession`（喂真实 10B 负载 + 坏体，
要求"不报错、不回帧"）。

### 15.2 `tuto_flags` 是什么用途（用户直接问的那一格）

- 脚本侧（`unpackdat\script\event\navi_*.nut`，每个 UI 一条）：
  `if( !GameState.getTutorialFlags(N) ){ GameState.setTutorialFlags(N); }`

- C++ 侧 `sub_42A570`（`GameState.setTutorialFlags(id)` 的落地，`0x42A570`）：

### 15.4 建号势力闸门（用户："创建机师时没有判断势力是否重复……应该发现后直接拒绝"）

口径：一个账号在每个势力（联邦 0 / 吉翁 1）**各最多一个在用机师**。两个要点：

1. **请求里的 `troops` 是客户端填的**，服务端不能反推"玩家想选另一个势力"（那会造出一个
   玩家没选的机师）。客户端建号页的军选择靠 `0xE13A` 的 `pilots_eff`/`pilots_zeon` 两张卡
   判断哪个势力还有空位（`UI/MakePilot_ArmySelect_01.nut` 只有显隐动画，逻辑在 C++）。
   ⇒ 服务端能做的只有"**这个势力已经有人 ⇒ 直接拒**"，回 `0xC43C result = ErrCodePilotTooMany`
   （与"超过两个机师"同码，客户端表现都是"建不了"）。
2. **判据取权威表**：`core.pilot_meta`（`0xE13A` 分卡就按它）为主，叠一道线格式侧
   （`game.pilots_list`/`game.pilot`）兜 meta 还没补行的老号 —— 只查线格式侧会漏
   （`loadListRecord` 读不到行就 `continue`，那一枪直接放过去）。
3. ★**软删的机师不参与判断**（用户 2026-09-22 第二轮补："已经删除的机师不应该参与判断，
   现在删掉之后同势力还是建不了"）。删号只打 `core.pilot_meta.deleted`，
   `game.pilots_list`/`game.pilot`/`core.pilot_registry` 那几行**一行不动**——
   所以第 2 条那道兜底必须"只管 meta 里没有行的机师"，否则它会把删掉的机师从线格式里
   捞回来当占位（`HasPilotInFaction` 答"空着"、兜底答"有人" ⇒ 建号被拒，
   而客户端连卡都看不到，症状是"没有机师却建不了号"）。
   判据 `store.PilotMetaIDs`：**meta 有行 = meta 说了算**（含 deleted 行）。
   同一个理由复查了名字判据：`PilotNameTaken` 与唯一索引 `uq_pilot_meta_name_alive`
   都是 `WHERE NOT deleted`，删掉的名字可以再用（两边口径一致才安全）。

落地：`lounge/pilot_handlers.go:accountHasPilotInFaction`（先 `Store.HasPilotInFaction`，
兜底前取 `Store.PilotMetaIDs` 把"有 meta 行"的 id 全部跳过）、
`store/pilot_meta.go:PilotMetaIDs`、
`lounge/pilot_create_faction_test.go`（同势力拒 + 一列不写 + 另一势力放行 +
两势力占满后第三个拒 + 闸门只看自己账号 + 软删不挡建号 + 删号准备期内仍拒 + 软删名可复用）、
`store/pilot_meta_deleted_db_test.go`（四条软删语义）。

**判据边界**（把真号 `world=1/account=2` 逐种状态点了一遍，五种全对）：

| 状态 | 同势力建号 | 依据 |
| --- | --- | --- |
| 势力里有**在用**机师 | 拒（`0xC43C = ErrCodePilotTooMany`） | `core.pilot_meta ... AND NOT deleted` |
| 势力里只有**已收尾**的号 | 放行 | 墓碑不算（用户 2026-09-22 要的） |
| 势力里的号**在删号准备期**（`del_requested_at` 有值、`deleted` 还是 false） | 拒 | 只认 `deleted`：倒计时里那张卡还在，势力就还占着 |
| 名字是**在用**机师的名字 | 拒（`ErrCodePilotNameTaken`） | `PilotNameTaken` + `uq_pilot_meta_name_alive` |
| 名字是**已收尾**号的名字 | 放行 | 同上，两边都按 `NOT deleted` |

**判定过程进日志**（用户 16:07 报的"同势力还能通过"，光有一行 `pilot_create ... troops=1`
什么也看不出来）：`accountHasPilotInFaction` 现在把"哪一道判据命中的、账号在用的是谁、
兜底跳过了谁"一起回来，两条路径都打 ——

```
[lounge] pilot_create 势力判定放行（account=2 troops=1）。判据：① ② 都没命中；账号在用=[1/troops=0]；兜底跳过=[2,3]
[lounge] pilot_create 势力重复 ⇒ 直接拒（account=2 troops=0 0xC43C result=-10105）。判据：① meta 权威表命中（该势力有 NOT deleted 的行）；账号在用=[1/troops=0]
```

（`兜底跳过=[2,3]` = 这两个 id 在 `core.pilot_meta` 有行 —— 墓碑也算，所以它们不再参与
"线格式占位"的判断；`②` 只有对"meta 里没有行的老号"才会命中。）

★"同势力还能通过"的观感只可能来自**上表第二行**（删号收尾之后同势力被释放）——
那是用户这一轮要的行为；准备期（第三行）仍然拦。若看到第一行/第三行也放行，
先查 `core.pilot_registry` 有没有那一行：闸门的两道判据（meta 权威 + 线格式兜底）
都要经 `ListAccountPilotIDs`（读 registry）才能把"账号 ↔ 机师"对上，
所以"线格式有行、registry 却缺行"的号，客户端画得出卡、闸门却看不见 ——
**这是已知窄口**（`ListAccountPilotIDs`/`PilotOwnedByAccount` 都只读 registry，
而 `game.pilots_list` 里没有 `account_id`，光靠线格式对不出归属）。
本服的正常路径不会造出这种行（建号 = `AllocatePilotID` 写 registry + 写 meta + 写线格式，
删号收尾只是把这三样一起收干净），它对得上"老服务端迁过来的、只留了线格式的号"。

### 15.4′ 删号收尾：墓碑 + 清存档（用户："别让软删态长期半截"）

删号分两步：**请求**（`del_requested_at`，倒计时里那张卡还在，客户端读 `del_remain_sec`）
与**收尾**（准备期到点）。收尾原先只打 `deleted = TRUE`，`game.*` 存档行与
`core.pilot_registry` 一行不动 ⇒ ①建号闸门的线格式兜底把删掉的号当成"占位"
（§15.4 第 3 条那个 bug 的现场）；②留下几十张表的孤儿行，而 `pilot_id` 一旦被回收，
新号就会继承前一个人的 `game.pilot_detail`（51KB）。

收尾口径（`store.FinalizePilotDelete`，一个事务）：

1. `core.pilot_meta.deleted = TRUE`（墓碑：名字释放、删除冷却、教程/MB 状态）；
2. 清 `game/core/srv` 里凡是有 `pilot_id` 的表（**自动发现**，不硬编码 60+ 张表；
   "行主 = `pilot_id`，别人的机师 id 带表名前缀"这条约定由真库测试钉住）；
   例外只有 `core.pilot_meta`（墓碑）与 `srv.lobby_notice`（公告发布当时的快照，0013 定案）；
3. `AllocatePilotID` 取号改成 `MAX(pilot_id)` over **registry ∪ meta** —— 归档会被清、
   墓碑不会，所以 `pilot_id` 单调不回退（清存档是尽力而为的，回收 id 等于让新号继承旧数据）。

三条收尾路径都走它：`0x6142`（准备期已过 ⇒ 当场收尾）、`0xE13A`/`sweepExpiredDeletes`
（登录或回大厅时扫过期）。幂等 + 自愈：已删过的号返回 `Deleted=false`，但墓碑说"已删"
时仍补扫残留（老实现留下的半截态就地收干净）；墓碑不存在/不属于本账号则一行不碰。
验收见 `store/pilot_purge_db_test.go`（五条）与 `lounge/pilot_delete_finalize_test.go`
（三条，含"未到准备期不许清"）。

### 15.5 顺带定案：三处"slot"分别是什么（用户问"solt 代表什么呢"）

同一个词三个意思，按上下文分：

| 出现在 | 含义 | 量纲 |
|---|---|---|
| `0xFD3E pilot_create.slot` / `0x7421` 无关 | **机师存档槽位**（选择机师页那张卡片的位置；`game.pilot` 的行键是 `(world_id, pilot_id, slot)`，本服建号写 `slot` 原值） | `u32` |
| `game.item.slot` / `inv_place` | **背包格子序号**（`srv.inventory_box` 决定容量；`0xF72A item_add` 带它） | `u16` |
| `game.ms_set.deck_slot` / `game.equip_set.equip_set_slot` | **机体装备/卡组的套装槽位**（`0x356F ms_set` 元素里的那格） | `u8` |

判据：看它是"行键的一部分"（机师槽）、"容量体系里的位置"（背包格）、还是
"同一台机体下第几套"（套装箱位）。三者在线上都不共用字段名，别互相套用。
