## §0 一句话结论

**商店的商品与价目**完全由服务端给（客户端 datafile 里**没有**商店表）：
客户端只报**页签号**（`0xD7B7` 1B）或**页签号 + 商品 id**（`0x44CF` 5B），服务端回
**整页陈列**（`0x99A0`，`9 + 23N`）或**单条**（`0xEA0F`，28B），每个元素 23B，带
**四种价**（`gp_x01/gp_x10/cp_x01/cp_x10`）、`bit_eff`、`stock`。
本服把这份数据放在 `srv.shop_lineup`，**行键 = `(tab_type, shopitem_id)`**，由 GM 配。
**页签枚举与 `id_type` 取值靠线上取证**（日志打印客户端实际请求值）；`bit_eff` 语义未取证，原样透传。

**买侧已接线**（2026-09-22 第二步，见 §6）：`CS-0xADB6 shop_buy` 只报"买什么、买几个、用
GP 还是 MB（`is_cp`）"，**价目与库存由服务端按 `srv.shop_lineup` 现查重算**（客户端上报的
`total_price` 只进日志）；结算在一个事务里做"扣钱 + 扣库存 + 发货"，成功后再由服务端推
**三条刷新**（道具 / 余额 / 陈列）——因为 `SC-0x2467` 的体只有 4B 的 `result`，客户端**不会**
因为买到东西而自动重拉任何界面。

## §1 读侧四条命令

| 命令 | 名 | 向 | 体长 | 字段（线序） | 客户端组装/去向 |
|---|---|---|---|---|---|
| `0xD7B7` | `shop_lineup` | CS | **1** | `u8 tab_type` | 组装 `sub_B9C9D0`（opcode @`0xB9CA44`，写线 @`0xB9CA53`） |
| `0x99A0` | `shop_lineup_r` | SC | **`9 + 23N`** | `u32 result`、`u8 id_type`、`u32 count`、N×23B `item_list` | 处理块 `0xB6E172..0xB6E480`，**去向 `vt[0x3A8]`@`B6E452`**，闭合 `B6E2AB` |
| `0x44CF` | `shop_lineup_one` | CS | **5** | `u8 tab_type`、`u32 shopitem_id` | 组装 `sub_B9CB80`（写线 @`0xB9CC09`/`0xB9CC15`） |
| `0xEA0F` | `shop_lineup_one_r` | SC | **28** | `u32 result`、`u8 id_type`、23B `item` | **去向 `vt[0x3AC]`@`0xB84747`**，闭合同块 |

- 三条 SC 的 `result` 都是 u32（负的错误码按二补数下发，对齐 `error_code.csv`）。

## §2 客户端侧（本轮复核）

### 2.1 商店 UI 类族（RTTI 实证，`detail\M01` §7.5）

`unpacked\shell\data_rt.bin` 里的类名（运行时 `.data` 段全量）：

`CShopMs_MsWindow` / `CShopMs_BaseWindow` / `CShopMs_MaterialWindow` / `CShopMs_PartsWindow` /
`CShopMs_PlanWindow` / `CShopMs_UseItemWindow` / `CShopRecycl_MsWindow`

⇒ 商店分页签（机体 / 基础 / 材料 / 部件 / 设计图 / 消耗品 + 回收），
**`tab_type` 就是这套页签的序号**。这也是"页签枚举没有常量表"的直接原因：页签语义在
客户端 UI 代码里硬编码，**不在 datafile 里**，服务端无从查表。

### 2.2 请求进入服务端对象的那一层（本轮新增证据）

三个 C→S 组装器各有一个**薄包装**，包装里先取全局门面 `sub_AF6E50()`：

| 包装 | 转发 | 参数（== 线序） |
|---|---|---|
| `sub_AFFF80(char a1)` | `sub_B9C9D0(obj, a1)` | `tab_type` |
| `sub_AFFFA0(char a1, int a2)` | `sub_B9CB80(obj, a1, a2)` | `tab_type`, `shopitem_id` |
| `sub_AFFFD0(int,char,int,char,int,int,int,int,int)` | `sub_B9CD70(...)` | 买侧 9 参（见 §6） |

`sub_AFFF80` 的唯一调用者是 `sub_6596E0`：它把 `a2` 存进 `this[333]`（当前页签），
并**按页签做"在途去重"**（`this[a2 + 324]` 置位，防同一页签重复发请求）
⇒ 服务端**必须每条 `0xD7B7` 都回包**，否则那一格标志不复位，玩家切回该页签会没有反应。

### 2.3 23B 元素（`sub_B458A0`）

```
offset  0 : shopitem_id u32   商店商品 id（空间由 id_type 决定）
offset  4 : gp_x01      u32   GP 价（买 1 个的总价）
offset  8 : gp_x10      u32   GP 价（买 10 个的总价）
offset 12 : cp_x01      u32   CP/MB 价（买 1 个）
offset 16 : cp_x10      u32   CP/MB 价（买 10 个）
offset 20 : bit_eff     u8    位效果标志（★语义未取证）
offset 21 : stock       u16   库存
```

- `cp_*` 就是**充值点（MB/ChargePoint）价**：它与 `is_cp`（买侧的结算开关）配对
  ⇒ 本链是"MB 消费"的主出口。
- `0xE13A pilot_list_get_r` 的 `bmgpack_list` 用的是**同一个复合体**（BGM 包陈列，
  上限 16 条），所以 BGM 商店的价格也走同一张表（不同 `tab_type`）。

### 2.4 仍未取证的两点（**不猜，线上取证**）

| 项 | 现状 | 取证办法 |
|---|---|---|
| `tab_type` 取值 | 客户端 UI 硬编码，无表可查 | 服务端日志 `[lounge] shop_lineup pilot=N tab_type=X`：客户端逐个切页签，抄 X |
| `id_type` 取值 | `0x99A0` 整页只回一个（= `shopitem_id` 的 id 空间） | 同上日志里的 `id_type=Y` + 客户端能否解析出名称/图标 |
| `bit_eff` 语义 | 客户端消费点未定位 | 原样透传：GM 试值，看客户端列表项的显示/可购状态 |

## §3 定源：为什么商店不在 datafile（这是本表存在的全部理由）

| 线索 | 结论 |
|---|---|
| `cfg/tables` 80 张表**无商店表** | 陈列（含价目/库存）不可能来自 datafile |
| `cfg.ITEM` 只有 `item_id/sort_group/name/description/item_type/stack_limit/linked_table_id/icon_variant` | **没有价格、没有库存** |
| `cfg.BGMPACKAGE` = 本地表（`class_name CBGMTable`），只有曲目 id / 资源路径 | 连 BGM 包价也没有 |
| `CS-0xD7B7` 只带 `tab_type`；`CS-0x44CF` 只带 `tab_type + shopitem_id` | 客户端**只问"买什么"，不报价** |
| `SC-0x99A0` 元素带 4 个价 + `stock` | 价目与库存**只能服务端给** |

⇒ `srv.shop_lineup`（与 `srv.channel` / `srv.chargepoint_price` 同口径：**服务端策略表**）。

## §4 服务端契约

### 4.1 表

```sql
srv.shop_lineup(
  tab_type     SMALLINT NOT NULL CHECK (0..255),   -- 页签（行键之一）
  shopitem_id  BIGINT   NOT NULL CHECK (0..2^32-1),-- 商品 id（行键之一）
  id_type      SMALLINT NOT NULL CHECK (0..255),   -- 商品 id 空间（一个页签共用）
  gp_x01/gp_x10/cp_x01/cp_x10 BIGINT CHECK (0..2^32-1),
  bit_eff      SMALLINT CHECK (0..255),
  stock        INTEGER  CHECK (0..65535),          -- 65535 = 无限
  label        TEXT,                                -- 备注名（不入线）
  sort_order   INTEGER, enabled BOOLEAN, updated_at TIMESTAMPTZ,
  grant_kind   SMALLINT CHECK (0..2),   -- 0019 买侧：0=入背包 / 1=机体（未接线）/ 2=只扣费不发货
  grant_id     BIGINT   CHECK (0..2^32-1), -- 0019 买侧：发货 id（0 ⇒ 用 shopitem_id）
  PRIMARY KEY (tab_type, shopitem_id)
)
```

- **行键即主键**：GM 的改/删按行键定位（`internal/gm/dbmeta.go` `pickRowKey`：无
  `world_id/pilot_id` 时取主键）⇒ 行键必须等于"运维脑子里的坐标"，否则改价要两步。
- **不加 `world_id`**：陈列全服一份；要多套再加列。
- **种子留空**：`shopitem_id` 必须是客户端认得的 id（空间未取证），不塞假 id。

### 4.2 读侧口径（`internal/lounge/shop_lineup.go`）

| 场景 | 行为 | 理由 |
|---|---|---|
| `0xD7B7` 页签无行 | `result=0`、`count=0`、`id_type=0`，体 **9B** | 空商店是可显示状态；**必须回包**（§2.2 在途标志） |
| 行数 > 500 | 截断到 500 并告警 | 客户端硬上界，超了写坏它缓冲 |
| 同页签 `id_type` 不一致 | 取首行，并把不一致行打进日志 | `0x99A0` 整页只有一个 `id_type` |
| `0x44CF` 找不到/已下架 | `result = -9403 (UnavailableItem)`（`0xFFFFDB45`） | `error_code.csv` 语义名；提示文案未逐步取证 |
| 读库失败 | 按空页签下发 + 日志 | 不把 DB 故障升级成客户端错误框 |

### 4.3 线长自检（服务端）

- `0x99A0`：`9 + 23N`；空页签 **9B**；满页 **9 + 500×23 = 11509B**。
- `0xEA0F`：**恒 28B**（`4 + 1 + 23`）。

## §5 运维手册

**首次上架（页签号未知时）**：

1. 客户端进商店，**逐个切页签**；
2. 看服务端日志：`[lounge] shop_lineup pilot=6 tab_type=3 => 0x99A0 id_type=0 count=0 body=9B`
   ⇒ 抄下 `tab_type`（先按 `id_type=0` 配）；
3. GM →「系统 / 服务端 · `srv.shop_lineup`」→ 按 `(页签, 商品)` **新增**行：填
   `id_type`、四价（`cp_*` 是 MB 价）、`stock`（65535=无限）、`bit_eff`、`sort_order`、`enabled`；
4. 客户端重开商店页签 ⇒ 列表出现；若某项名称/图标解析失败，说明 `id_type` 不对
   （改该页签全部行的 `id_type` 重试）。

**日常（读侧）**：限购/停卖 = 把 `stock` 改小或置 0；下架 = `enabled=false`（已购记录不受影响）；
调价 = 改 `gp_*/cp_*`（下一条请求即生效，无缓存）。

**日常（买侧，2026-09-22 起）**：

| 想要的效果 | 改哪里 | 说明 |
|---|---|---|
| 卖什么 | `grant_kind` + `grant_id` | `0`=发道具进背包（`grant_id` 是道具 id，`0` 表示"就用 `shopitem_id`"）；`1`=发机体**未接线**（这种行点了买会回 `-9403`，不会扣钱）；`2`=**只扣钱不发货**（上架灰度/联调用） |
| 卖多少钱 | `gp_x01/gp_x10/cp_x01/cp_x10` | `*_x01` = 买 1 个的**总价**、`*_x10` = 买 10 个的**总价**（不是单价乘 10）；某档填 `0` = **该档不可买**（不是免费） |
| 能不能买 | `stock` / `enabled` | `stock` 每成交一单就减（`65535` = 无限，不减不耗尽）；`enabled=false` 回 `-9403` |
| 玩家钱不够时的提示 | — | 回 `-26007`（GP 不足）/ `-8513`（MB 不足）/ `-18006`（背包满），客户端查 `error_code.csv` 出文案 |
| 只看某个页签对不对 | 服务端日志 `[lounge] shop_lineup / shop_buy …` | 买侧的日志一行含 `tab_type/shopitem_id/num/is_cp/client_price/result/price/balance/stock/granted`（`client_price` 与 `price` 不同只留证不拒绝，按服务端价结算） |

**注意**：买侧**没有**"客户端会自己刷新"这回事 —— 余额、背包、陈列三处刷新全部由服务端在
`SC-0x2467` 之后补推（§6.2）。所以"点了买没反应"先看服务端有没有发出那四条推送。

## §6 买侧定案（`CS-0xADB6 shop_buy` ⇒ `SC-0x2467`，2026-09-22）

### 6.1 命令与线格式

| 命令 | 名 | 向 | 体长 | 字段（线序） |
|---|---|---|---|---|
| `0xADB6` | `shop_buy` | CS | **变长** | `u32 shopitemid`、`u8 id_type`、`u32 num`、`u8 tab_type`、**`u8 is_cp`**、`u32 total_price`、`str gift_pilot_name`、`str subject`、`str body`（后三串是赠礼/邮件） |
| `0x2467` | `shop_buy_r` | SC | **4** | `u32 result` |
| `0x090C` | `pilot_money_update` | SC | **4** | `u32 money`（GP 余额） |
| `0x02F6` | `chargepoint_update` | SC | **4** | `u32 chargepoint`（MB 余额，与 W23 月卡同一条出口） |
| `0xF72A` | `item_add` | SC | **24** | `u16 inv_place` ＋ 22B `item`（新实例） |
| `0xD563` | `item_stack_update` | SC | **10** | `u64 uniqid`、`u16 stack`（叠加） |
| `0xAB7B` | `shop_lineup_notify` | SC | **变长** | `u32 id_type_num`、`u8[n1] id_type`、`u32 item_num`、`23B[n2] item_list` |

- `num` 只可能是 **1 或 10**（客户端只有 ×1/×10 两档，`sub_659770`）；`is_cp = 1` 扣 MB、
  `0` 扣 GP —— 与 `cp_*` / `gp_*` 两组价一一对应。
- **`total_price` 不可信**：它是客户端按**屏上价目**自算的显示值（连"GP 不足"都是它本地先弹的），
  服务端按 `srv.shop_lineup` 重算；两者不一致只打日志（拒绝会表现为"点了没反应"）。

### 6.2 客户端侧（本轮 IDA 新增证据）

| 事实 | 证据 |
|---|---|
| 买请求发出前把"在途"标志置 1，**只有收到 `0x2467` 才清 0** | `sub_659770`（置位）→ `sub_659DE0`（首行清位） |
| `0x2467` 的消费者**只把 `result` 转交给"当前打开的那个商店窗口"**（按窗口类分派），**没有任何重拉陈列/背包/Actions** | `sub_659DE0` → `sub_86E510`/`sub_874580`/`sub_86AB60`/`sub_877960` … |
| `0xAB7B` 是 `(id_type, item)` **成对**下发，且**必须 `n1 == n2`**（`sub_65E970` 只按 `n1` 转，`n2` 从未被读） | 出口 `vt[0x3B0]`@`0xB71C15` → `sub_BACC90` → `sub_AF8CC0` → `sub_65E970` |
| `0xAB7B` **按 `shopitem_id` 插入、已存在就什么都不做**（不是改价通知） | `sub_65E680`（`sub_65AED0` 查表命中即返回；未命中才插 ×1/×10 两条） |
| 赠礼（`gift_pilot_name` 非空）走"买给别人 + 邮件"，本服未接线 | `0x7BCC item_add_dialog_show` 等未接线 |

⇒ **服务端必须推**：GP ⇒ `0x090C`、MB ⇒ `0x02F6`（客户端在发请求**之前**就本地比过一次余额，
不推就会拿着旧值再点一次并被本地弹 `-26007`）；新实例 ⇒ `0xF72A`、叠加 ⇒ `0xD563`（钱包与背包
是两套 UI）；陈列 ⇒ `0xAB7B` 单条（净效果是"让新上架的商品出现在当前页"，改价/改库存要靠客户端
下次开页签或 `0x44CF` 现查库）。

### 6.3 服务端契约

**加的两列 + 一个发号器**（`0019` / `0020`）：

| 对象 | 作用 |
|---|---|
| `srv.shop_lineup.grant_kind`（`0`=item / `1`=ms 未接线 / `2`=none 只扣费） | 买了发什么；`ms` 在**扣费之前**就拒（`-9403`） |
| `srv.shop_lineup.grant_id`（u32） | 发货 id；`0` ⇒ 用 `shopitem_id` 本身 |
| `game.item_uniqid_seq`（起始 `10^12`） | 新道具实例的 `uniqid` 发号（避开手工小 id）；客户端拿它做后续单件操作（如 `CS-0x457B`） |

**两种货币**：GP ⇒ `game.pilot_detail.money`、MB ⇒ `core.pilot_meta.charge_point`；两者都只走
"窄 UPDATE"，且**守卫写在 WHERE**（`money >= 价` / `charge_point >= 价`）—— 双开/连点不会超扣。

**一笔买的全部动作在一个事务里**（`internal/store/shop_buy.go` `BuySrvShopItem`）：

```
① SELECT … FOR UPDATE       锁商品行（关掉"并发改价/改库存"的窗口）
② PriceFor(num, is_cp)      重算价；档位 0 价 = 不可买
③ grant_kind 校验           未接线（ms）⇒ 在扣费前拒
④ 扣库存                    stock 每单递减（65535 = 无限，不动）
⑤ 扣钱                      UPDATE … WHERE 余额 >= 价（不够 ⇒ 回码，不进下一步）
⑥ 发货                      同 item_id 先叠（stack 不溢出 u16），否则在主栏 [0, main_cap) 找最小空格
⑦ COMMIT                    任一步失败/拒绝 ⇒ 整笔回滚（钱、库存、背包同时不动）
```

**回码**（客户端 `error_code.csv` 的语义名，负数按二补数下发）：

| 码 | u32 线值 | 语义 | 触发 |
|---|---|---|---|
| `0` | `0` | 成功 | — |
| `-9403` | `0xFFFFDB45` | 无法购买的道具 | 商品不存在 / 已下架（`enabled=false`）/ 档位无价 / 库存不足 / `grant_kind=ms` 未接线 / 赠礼未接线 / 结算基础设施故障 |
| `-26007` | `0xFFFF9A69` | GP 不足 | `money < 价`（客户端本地也会先判一次） |
| `-8513` | `0xFFFFDEBF` | MB 不足 | `charge_point < 价` |
| `-18006` | `0xFFFFB9AA` | 仓库已满 | 主栏 `[0, main_cap)` 无空格 |

**`inv_place` 口径**：新实例一律落在**主栏**（`grantShopItem` 的空格搜索范围是 `[0, main_cap)`，
`main_cap` 与 `SC-0x02EE` 下发的 `slot_num_main` 同源 —— 都取 `srv.inventory_box`）。主栏是四栏
区间的第一段、起址为 0 ⇒「全局槽位索引」与「主栏内序号」两种读法**同值**，避免在口径未完全
取证时发一个二义的数。**叠加不改 `tm_sec/tm_usec`**（`0xD563` 体里没有时刻，改了会与客户端显示不一致）。

**赠礼未接线**：`gift_pilot_name` 非空 ⇒ **扣费之前**直接回 `-9403`（免得钱扣了货发不出去）。

### 6.4 线长自检（服务端）

- `0x2467`/`0x090C`/`0x02F6`：恒 **4B**；`0xF72A`：恒 **24B**（`2 + 22`）；`0xD563`：恒 **10B**。
- `0xAB7B`（单条形式）：`4 + 1 + 4 + 23 = 32B`。
