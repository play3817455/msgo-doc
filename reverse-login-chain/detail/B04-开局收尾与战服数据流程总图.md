## 1. ★更正：`game_begin`(0x1365) 的 4 个数组是**并列**，不是嵌套

B03 记为"两级嵌套数组块"。2026-09-15 用 case `0xB0FE94..0xB1004C` 的**循环回边**实测订正：

```
u32 n1  ≤0x32(50) ; 循环 n1 次：sub_B079A0(每条 58B 线 / 80B 槽)，槽步长 += 0x50
u32 n2  ≤0x20(32) ; 循环 n2 次：sub_B07BD0(每条 52B 线 / 188B 槽)，槽步长 += 0xBC
                        sub_B41740(取 20B) + sub_B07E00(**单条** 14B / 20B 槽)
u32 n3  ≤0x0B(11) ; 预留 n3×4 → n3 × u32
u32 mission_phase
```
⇒ **4 个并列数组**，与 dump 第 16~20 名一一对应：
`respawn_posts[]`(①,≤50) / `mapgimmicks[]`(②,≤32) / `bgm_desc`(③,**单条**) / `missionunit_set[]`(④,≤11) / `mission_phase`。

**★`bgm_desc` = 单条（静态铁证，非猜测）**：`formats/_battle_case_trace.txt` L289~L303 逐指令
——②号数组的循环回边落在 `00B0FF9A`；紧接 `00B0FFA3 call sub_B41740`（取槽，**前置无任何 count 读**）+ `00B0FFB2 call sub_B07E00`（14B 单条解析器）；
错误处理器边界 `push 1/push 32h/call eax`（`00B0FF92`）与 `00B0FFBC jz loc_B0FC43` 把该组**定义为恰好一条**；
其后 `00B0FFCC call sub_B02DD0`（count）+ `00B0FFDC cmp …,0Bh`（≤11）+ `00B0FFF8 call sub_B41850`（预留 n×4）才是④号数组 ⇒ 两个 count **不可能**属于 `bgm_desc`。
⇒ 与 B03 的"两级嵌套"猜测相反，但与本文件实现（`protocol.EncodeGameBegin` ③ 单条 14B）一致 ✓。

**元素线长（= 解析器实际消费字节）**：
| 结构 | 线长 | 槽 | 字段宽度序列（服务端按此填，语义名客户端未给） |
|---|---|---|---|
| `respawn_posts` 元素 | **58B** | 80B | `u32,u16,u16,u8×13,u32,u32,u16×4,u8,u32×4` |
| `mapgimmicks` 元素 | **52B** | 188B | `u8,u8,u16,u32,u32,u32,u16×7,u16×2,u16×9` |
| `bgm_desc` | **14B** | 20B | `u8,u32,u32,u32,u8` |

**体长核算**：`126(前 15 字段) + (4+n1×58) + (4+n2×52) + 14 + (4+n3×4) + 4`
⇒ 空数据（n1=n2=n3=0）= **156B**；上限 50/32/11 全满 ≈ `126+2904+1668+14+48+4 = 4764B`（alloc 上限 10246 ✓ 余量充足）。

> ★★**2026-09-15 更正**：前 15 字段 = **126B**（不是 120B ✗）—— 因为 `config` 线上是 **34B**（不是 28B ✗，见 B03 §2-a）。
> `config` 结构体 40B（客户端用 `sub_B418C0` 预留）只说明结构大小，**不是**线上长度。

## 3. 实体同步数据流程（`internal\battleworld`）

```
客户端A 本地模拟：0x421B pos_move（客户端权威，尾部 hack_check{} 服务端只收不判）
        ┌──────────────────────────────────────────────┐
        │  World 实体表（EntID/Team/Pos/Dir/Target/     │
        │  HP%/盾%/EquipIndex/Water/Layer/Rideon/      │
        │  Lockon/SpecialBits/特殊事件参数 score1..3）  │
        └───────────────┬──────────────────────────────┘
                        │ Entries() 按稳定顺序投影
        protocol.SnapshotEntry（= 客户端 44B 槽的 21 字段，B06 定名）
                        │
        ┌───────────────┴───────────────┐
        │ 0x568A 逐条：12B 头 + N×39B    │ ★二者可选，MVP 建议只发列式
        │ 0x5EEA 列式：8B 头 + 31 列，   │
        │        每列 u32 count+count×元素│
        └───────────────────────────────┘
```
- `World.Tick(remainMsec, useFull)` = `frame++` + 产出报文（`useFull=false` 只出 0x5EEA）。
- 列式的好处：**每列 count 独立** ⇒ 只发变化的实体（delta）；MVP 用 `SplitDeltaFromEntries()`
  （所有列 count=N + `dirty_bits=0xFFFF`）即"全量语义"，**绕开 dirty 位映射未知的风险**。
- `World.ApplyDamageResult(entID, hp%, shield%)` = 把**服务端结算结果**回写世界（供下一帧快照）。

## 4. 伤害数据流程（`internal\battledmg`）

```
客户端A 本地判定命中 → 上行 0x770D weapon_hit_to
   （★包里**没有** damage/hp：只有 phash/frame/weapon_itemid/fire_id/
     8 个 ≤16 元素的 u16 数组(ent_ids/hit_pos_xyz/hit_dirs/hit_distance/body_distance/body_regions)/
     charge_lv/AI_ent_id/instate_from_ent_id/create_frame_count/is_down_range/is_wrestle_first）
        ↓ ResolveAll(hit, stats)：逐目标
        │   power = |POWER|（回复类取负 → 治疗路径）
        │   raw   = power × chargeMul × BodyRegionMul × rateA × rateB
        │   defMul= 1 − clamp(def/(def+400), 0, 0.8)      // 软化，避免负伤害/除零
        │   dmg   = max(1, raw×defMul)
        │   先扣盾 → 剩余扣本体 → hp=0 ⇒ Dead
        ↓
下行  0x49C6 weapon_hit_from（**43B**，含 hp_now/hp_max/damage/shield_hp_now）
      0xF4D7 shield_any_damage（走盾时补发，6B）
      0xDDF7 weapon_hit_to_r（给射手的回执，16B）
      0x9105 entity_msma_dead(28B) + 0x844B kill_count_update(23B) + 0x8D59 score_update(28B)
```
**表口径（服务端真值，客户端不参与结算）**：
- `msma/msma_battle_detail.csv`：`MAX_HP` / `COST` / `MOVE` / `BOOST_*`（670 台）
- `item/weapon_battle_detail.csv`：**`POWER`** / `RANGE` / `STABILITY` / `LOCKON_CAM` / `HIGH_LOCKON` / `RAPIDDELAY`；
  ★`POWER` 在 6 个回复类类别时取负（`REPAIR / WRESTLE_REPAIR / RESURRECT / BULLET_PACK / REPAIR_PACK / REPAIR_THROW`）
- 129 条 `MS_*` 属性：`MS_ARMOR / MS_DEF_SOLID|BEAM|BLAST / MS_DEF_PLACE_GROUND|WATAR …`
- 伤害倍率 `Rate{A,B}` = 服务端下发（客户端 `sub_4419F0` 的 `DAMAGE RATE RECVED`）
