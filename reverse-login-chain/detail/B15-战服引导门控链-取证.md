## 0. 结论先行：四步引导序列（★服务端照此发，顺序不能换）


## 1. ② `0xA5DA` 的处理链与落点（`sub_BA8C20 → sub_AFAB40 → sub_448FE0(app, 20 参)`）

**调用链**（全部 byte-exact）：
```
vt+0x70 = sub_BA8C20(this=proto对象, a2..a22)     ; this[16584] = (a2 >= 0)  ← 成功标志
        → sub_AFAB40(a1..a20)
        → sub_448FE0(app = dword_11E3EA8, a2..a21)
```
- `sub_BA8C20` 只有一句有效代码：`this[16584] = a2 >= 0`（`0x40C8` = 战斗服协议对象的"上一次认证是否成功"）。
- `sub_AFAB40` 是**纯转发**（`app` 由它补上）。
- ⇒ **真正的实现 = `sub_448FE0`**，参数 20 个，与 `0xA5DA` 的 **20 个线上字段 1:1**。

**1:1 对齐的两个锚点（不是猜）**：

## 2. ③ `0x1365 game_begin` 的处理链与**三道门**（`sub_BA9120 → sub_AFAF90 → sub_44B150`）

**调用链**：
```
vt+0xEC = sub_BA9120(a1..a23)
   1) dword_120A970 = 0
   2) 零 52B 局部结构 + 填：v24[0..4]=a1..a5  v24[6]=a6  v25=a7  v26=a8
                              v27=a9  v28=a10  v29=a11  v30=a12  v31=a13   （v24[5] 恒 0）
   3) sub_AFAF90(&v24, a14..a23)          → 纯转发 → sub_44B150
   4) if (a8 /*is_room_suspend*/) sub_AFB060() → sub_445560(1)   ; ★房间挂起 ⇒ 暂停处理
```

**`sub_44B150` 开头三道门（★顺序铁律的技术根据）**：
```c
v15 = (*(app+416220) == 0);
if (!v15) {                                  // 门①：只有 0xA5DA 置过它
    if (sub_AF7070()) {                      // 门②：战斗服会话就绪
        if ((*(app+114268) & 4) == 0) {      // 门③：不是"已在战场"
            ... 初始化 + 压状态步 ...
        }
    }
}
```
- **门①** `app+416220` —— 只由 `0xA5DA`（`sub_448FE0`）置 1。
- **门②** `sub_AF7070()`（新取证）：
  ```c
  v0 = (dword_1201A64 + 16576);            // battle proto 对象的会话字段
  return *(dword_1201A64 + 16580)          // 会话对象存在
      && (session->vt[16/4](session) == 3 || session->vt[16/4](session) == 4);  // 状态 3/4 = 已连/握手完
  ```

- **门③** `app+114268 & 4`：置位表示"已在战场"，防止重复初始化。
- 同文件已有便捷判据（离线 dump 亦可见）：`sub_43F7F0` = `app[416220] && sub_AF7070()` ⇒ **"战场就绪"的官方判据**。

## 3. 状态步 vtable 对照（两个都是"数据步"，tick 在 **+0x08**）

| 类 | vtable | +0x00 | +0x04 | **+0x08 = tick** |
|---|---|---|---|---|
| `CGameStateStepUpdateLoginBattle` | `0xD68474` | `sub_A87AF0` | `nullsub_1` | **`sub_440080`**（state0 连战斗服 / 1 等就绪 / 2 发 0xF24B / 3 空转） |

## 4. ④ `0xE041 msma_spawn_list_get` 的触发点与"三连"要求

**触发链（客户端自动发，无需服务端催）**：
```
状态步 CGameStateStepUpdateMSMAList 的 tick = sub_440C90
  state0: app+115292 = 0; app+115288 = -1;   ← 清列表/选中态
          if (sub_B01220()) ++this[1];       ← sub_B01220 = "会话就绪则发送"
  state1: return 0;                          ← ★等（等 0x9951/0x1E2F/0xAB6F 收完）
  state2: *(this[5] + 60) |= 1; ++this[1];
  state3: return 1;                          ← 完成
发送函数：sub_B01220 → sub_B33DA0（= 0xE041 打包器，**体空**）
```
⇒ 服务端必须回 **三连**：`0x9951 r_begin(8B)` → `N×0x1E2F r_one(4+244B)` → `0xAB6F r_end(0B)`；
**缺 end 或顺序错 ⇒ state1 永远返回 0 ⇒ 客户端卡在"选机前"**（不报错、不断连）。

**⑤ `0xE650 msma_spawn_select`**（选机）⇒ 回 `0x86B2 select_r`（22B）。之后的出击族（`0xFEBB/0xE5FC/0x8DE4/0x717D`）见 B05。

## 38. ★★★★★ 收官：C→S 92 条**全部有专用实现**（78 真实现 + 14 专用解析 + 0 兜底）

### 38.1 ★★新方法：用 `hist` 反推字段宽（"字段表与 `sum` 不一致"的死结解法）
`battle_bodylen.json` 每条都有 **`hist` = 各读取函数的调用次数**（多集，如 `{"sub_B41470":2,"sub_B02DD0":2,…}`）。
把"读指针推进器"与"取值器"配对，就得到**实际线宽**：

| 推进器 | 取值器 | 线宽 | 贡献 |
|---|---|---|---|
| `sub_B41470` | `sub_B02DD0` | u32 | 4×N |
| `sub_B413B0` | `sub_B02DF0` | u16 | 2×N |
| `sub_B05E30` | `sub_B06230` | u8 | 1×N |
| `sub_B02BA0` 等 | — | 变长（串/数组） | **不计入** `sum_fixed` |

⇒ **Σ = 4×u32 + 2×u16 + 1×u8 必须等于 `sum_fixed`**（实测 205 条里 **180 条**咬合 ✓）。
判读：Σ 与字段表不符时，用 Σ 反推"哪个字段比 hint 窄"；**顺序**再靠反汇编看（`entry` 字段即 case 体地址，
读序是 `peek → accessor` 成对出现，如 `0xC166` 那条）。

★**副产品：它能反向验证我们已实现的布局** ——
`0x1A13 hand_throw_r` = 4×2+2×9+1×3 = **29** ✓、`0x37C1 for_myself_r` = 4+2×3+1 = **11** ✓、
`0x049D chase_move_start_r` = 4×2+2×6 = **20** ✓、`0x03CC air_bomb_r` = 4×2+2×4+1×2 = **18** ✓
