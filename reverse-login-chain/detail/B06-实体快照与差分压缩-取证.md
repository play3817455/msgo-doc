# B06 · 实体同步：`entity_snapshot`(0x568A) 与 `entity_snapshot_splitdelta_compress`(0xBAE4)

> 2026-09-15 IDA 实测。**结论先行：服务端可以先只发"非压缩快照"就能让客户端看到人** —— 两条路径最终汇合到同一个消费入口 `vt+0x180`。
> ⇒ `zbuff` 压缩编码**不是 MVP 的阻塞项**。

## 1. 两条 S→C 报文

| 报文 | ID | 闸门 | 解析序列（按地址） | alloc | handler |
|---|---|---|---|---|---|
| `entity_snapshot` | **0x568A** | 97 | `u32 frame_count` │ `u32 remain_msec` │ `u32 count` │ **count × 44B 实体块**（逐条用 `sub_B075A0` 解析） | `0x8F0C = 36620` | `vt+0x180 = sub_BA9740 → sub_AFB4C0` |
| `entity_snapshot_splitdelta_compress` | **0xBAE4** | 99 | `u32 frame_count` │ `u32 remain_msec` │ `u32 zbuf_len` │ `zbuf_len × u8`（压缩流） | — | `vt+0x188 = sub_BA9990` |

**`sub_BA9990`（压缩版 handler）**：
```c
sub_AA2AF0( zbuf_ptr, zbuf_len );                                  // ★解压到全局缓冲
return (*(vt+0x180))( this, frame_count, remain_msec, &unk_1201A70, dword_120A970 );  // ★与"非压缩版"同一个入口
```
⇒ **压缩版 = 解压后走同一条"应用快照"路径**；`&unk_1201A70`/`dword_120A970` = 解压结果（实体块指针）与条数。
⇒ **两条路等价** ⇒ 先发非压缩的 `0x568A` 即可（带宽更大但零风险）。

## 2. ★实体条目布局（`sub_B075A0`，**44 字节/条**，客户端游标 `cur += 0x2C`）

`entity_snapshot` 的循环（case 0xB1812A..）实测：
```
count ≤ 0x340(832)                        // 超过报错
sub_B06030(&block, &cur, count)           // 记下块起点，游标先跳过 44*count
for (i=0; i<count; ++i) {                 // 逐条解析
    sub_B075A0(&ent, cur);                // 读一条（下面 21 个字段）
    cur += 0x2C;                          // ★固定步长 44
}
```

`sub_486900` 反汇编（byte-exact，edi = 条目指针，esi = 实体对象）：
```
movsx edx,[edi+2]  ×[dword_11E3EA8+0x1C230] → [esi+0x34]   ; pos_x（系数 K 在全局 +115248）
movsx ecx,[edi+4]  ×K → [esi+0x38]                          ; pos_y
movsx edx,[edi+6]  ×K → [esi+0x3C]                          ; pos_z
movsx edx,[edi+8]  ×flt_D69A68 ×flt_D91AF8 → sub_BE2300 → [esi+0x5C/60/64/68]  ; dir → 单位方向向量（再乘 flt_110BD34/38/3C）
movsx ecx,[edi+0x20] → [esi+0x114]                          ; ★状态/动作 id
test word ptr [edi+0x2A], 7000h                             ; ★门控：槽位 0x2A 的 0x7000 位
   （且实体 [esi+0Ch] & 2）→ 触发 dword_11E3EC8 的 vt+0x20(eax, [edi+0x0C], [edi+0x10], [edi+0x14])
```
- 进入 `sub_486900` 前，实体上一帧被保存（`[esi+0x40/44/48] ← [esi+0x34/38/3C]`；`[esi+0x6C/70/74/78] ← [esi+0x5C/60/64/68]`）⇒ 客户端据此做插值。
- `sub_4C1D00` 的门：`if ( *(u16*)(entry+0x2A) )` 才按 `s16 @0`（ent_id）查找实体并调用 `sub_486900`。

**上限/容量**：`count ≤ 832 (0x340)`；每条槽位 44B，缓冲 `alloc = 36620 (0x8F0C)` ≈ 832×44 + 12 ✓ 完全吻合。
（该缓冲 = 消息级临时缓冲：`[client+0Ch]→vt+0x78(0x8F0C)`，`sub_B06030` 在缓冲里"预留 count×44B"并把指针推到位。）

### 2.2 槽位 0x2A（wire 之后 3 字节）由谁写？ —— **已定论：= `splitdelta` 的 `dirty_bits`**
- 39B 的解析器不写 0x2A，但 `sub_4C1D00` 用它做"条目有效"门控、`sub_486900` 用它做"开火/特效事件"门控 ⇒ **必须非 0 才有实体同步**。
- **答案（B06b 交叉定案）**：`entity_snapshot_splitdelta`(0x5EEA) 的列式快照第 2 列就是 **`dirty_bits[]`（u16）**，它按 44B 槽的**同一布局**装配（同由 `sub_AA2640` 列式装配器消费）⇒ **0x2A-0x2B = `dirty_bits`**；`0x568A`（39B 全量线序）里没有它 ⇒ 空洞。
- ⇒ **对 `0x568A`，0x2A 只能靠"上一次 0x5EEA 遗留值"**（客户端 buffer 复用）：刚起的战场若只发 0x568A，0x2A 可能为 0 ⇒ 实体**不更新**。这是"必须走 0x5EEA"的**结构性原因**（不只是带宽）。
- **★位映射：不可能是"一列一位"**——列式快照共 **31 列**，而 `dirty_bits` 只有 **u16 = 16 位**，装不下 30 个非自身列 ⇒ 它是**分组/事件位**（多列合并成位），而非逐列掩码。客户端消费端只显式测 **`& 0x7000`（bit12/13/14）** + "非 0" 两道门。
- ⇒ **服务端取值结论**：**全 `0xFFFF`** 是唯一两头都安全的值（非 0 ⇒ 过 `sub_4C1D00` 门；`& 0x7000` ≠ 0 ⇒ 过 `sub_486900` 门；且"全脏"语义 = 全字段刷新，与全量快照等价）✓ 已落地 `protocol.SplitDeltaFromEntries`。
- 残余（**不阻塞**，仅影响带宽优化）：位↔分组的确切语义未知 ⇒ 只要用"全列 count=N + 0xFFFF"就用不到它；将来要做真 delta 时，在 `0x486A2F test word ptr [edi+2Ah],7000h` 断点看真机值 + `sub_AA2640` 参数表反推。

### ★0x2A 未解项 → 已定论
- 打印器**没有** 0x2A 字段；解析器 `sub_B075A0` 也不写 0x2A；39B 线序 = 上表 21 字段之和 ✓✓
  ⇒ **`0x2A-0x2B` 是该内存槽的空洞（线上不传）**。
- 但 `sub_4C1D00` 用 `*(u16*)(entry+0x2A)!=0` 做门控、`sub_486900` 用 `& 0x7000` 做开火/特效门控
  ⇒ 说明这两个消费函数**同时服务另一条报文**：**`entity_snapshot_splitdelta`(0x5EEA)** 的列式条目含 **`dirty_bits[]`**，正是写进 0x2A 的"变化位"。
- ⇒ **对 `0x568A`（全量）服务端只需发 39B/条；若发现客户端不更新实体，改用 §2ter 的 0x5EEA 路径。**

## 2ter. ★★结论修正：MVP 建议改发 **`entity_snapshot_splitdelta`(0x5EEA，列式、无压缩)**
| 报文 | 结构 | 是否需压缩 | 0x2A 语义 |
|---|---|---|---|
| `entity_snapshot` **0x568A** | 逐条 44B 槽（线序 39B） | ✗ 不需要 | 空洞（dirty 位缺失） |
| **`entity_snapshot_splitdelta` 0x5EEA** | **列式(SoA)**：`frame_count, remain_msec, ent_id[], dirty_bits[], pos_real_x/y/z[], pos_diff_x/y/z[], dir[], target_real_*, target_diff_*, spbit_ll/l/h/hh[], spbit2[], hp_percent[], hp_percent_shield[], down_power[], equip_index[], score1..3[], water_index[], layer_index[], rideon_ent_id[], lockon_ent_id[]` | **✗ 不需要** | ✔ dirty_bits 正确 |

  ⇒ **先实现 0x5EEA 即可**：既避开编解码器，又拿到正确的 dirty 位语义；压缩版以后再补。

## 3. `zbuff` 压缩：**iVCE SDK 编解码器**（不是自定义算法）

调用链：
```
sub_AA2AF0(zbuf, len)
   ├─ sub_C85F50()                       // SDK: 会话/状态初始化
   ├─ sub_C86010(zbuf, len, &out_len, &hdr)   → sub_CB7350(...) → sub_CBDA80(state, 4)
   │        // ★SDK 的"压缩/解压"引擎：喂 (src, srclen, dst, dstcap)，回 out_len；内部分 4 段状态机
   ├─ sub_AA2640( 60+ 参数 = 各"列"指针/长度 )   // ★把解压结果（列式 SoA）装配成实体块
   └─ sub_C86400()                       // 释放
```
- 解压输出缓冲 = **29952 (0x7500)** 字节（栈上 `v59[29950]`）。
- **可用编解码器**：SDK RTTI 里同时存在 `iCompressSession<LZP,…>` 与 `iCompressSession<ZLIB,…>`（还有 Camellia/Rijndael 加密会话模板）；
  exe 还引了 **`zlib1.dll`（`compress2` / `uncompress`）**，并有 `..\DataCompress\Derived\DataCompressZlibDerived.cpp` 与 `sel_compression` 字符串 ⇒ **压缩方式是可选的**（LZP 或 zlib），需要时再确认 `sub_CBDA80(state,4)` 的 4 段是哪一种。
- **MVP 结论**：**不要碰它**——直接发非压缩 `entity_snapshot`。

## 4. 消费端（应用快照）
```
vt+0x180 = sub_BA9740 (16B thunk) → sub_AFB4C0(this, frame_count, remain_msec, 块, count)
     ├─ sub_4401D0(this, frame_count, remain_msec)
     │     *(this+115264) = frame_count
     │     *(this+310624) = frame_count × flt_D68748     ← 帧→时间
     │     *(this+310628) = remain_msec × flt_D68748     ← 毫秒→时间（供插值/延迟补偿）
     └─ sub_4C1D00(this, ?, 块, count)
           for (i<count) { if (*(u16*)(entry+0x2A)) { id=*(s16*)entry; 找到实体 → sub_486900(entry,0); } entry += 0x2C; }
```

## 5. 服务端落地建议（本项）
1. **S3/S4 阶段先只实现 `0x568A`**：`{u32 frame_count, u32 remain_msec, u32 count, count×39B}`（39B 按 §2.1 表；若 §2.2 验证出 0x2A 需非 0，再按结论补）。
2. `count` 建议 ≤ 832（硬上限），节拍用 `game_begin` 的 `snapshot_int_msec / snapshot_res_msec`；`frame_count` 单调递增，`remain_msec` 给"本帧剩余时间"。
3. 坐标/朝向是 **s16 量化**：`世界坐标 = s16 × K`，`K = *(dword_11E3EA8 + 0x1C230)`（全局，客户端读；服务端需用同一 K 反算）。
4. `recv_pos_warp_force`(0xC327, **12B**：`ent_id,pos_x,pos_y,pos_z,dir,reason` 全 u16) 可用于"纠正"表现（可选）。
5. 之后若要压缩：先确认 SDK 用的是 LZP 还是 zlib（`sub_CBDA80` 的 4 个状态分支），再决定移植。
