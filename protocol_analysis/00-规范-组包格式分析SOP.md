# 组包格式分析规范（SOP）

> 本规范是本目录的**唯一作业依据**。任何一条命令的分析产物必须满足本规范。
> 本目录为**全新分析**：不引用、不复制本目录以外的任何历史结论；一切以本轮 IDA 静态证据为准。

---

## 0. 一句话目标

把客户端（`GundamOnline_CHINA_v15.exe`，ImageBase `0x400000`）与服务端之间往来的**每一条命令**，
落成一份可复核的**线格式（wire format）定义**：

> 字段顺序、偏移、长度、类型、含义、用途 —— 每一项都必须有**汇编级证据**。

---

## 1. 三条铁律（最高优先级）

1. **类型只能来自汇编，伪代码不算证据。**
   Hex-Rays 反编译出的变量声明类型（`int` / `unsigned __int16` / 结构体类型…）
   **禁止**作为字段线类型的依据。伪代码只允许用于**定位与控制流浏览**。
   字段宽度一律由读/写指令的操作数宽度判定（见 §5）。

2. **线长 = 读取器/写入器实际消费的字节数。**
   以下都不等于线长：
   - `alloc(N)` / `vt[0x78](N)` 的 `N`（是**缓冲容量**，通常大于等于线长）；
   - 内存结构体的大小（如 `add [ecx], 138h`）——与线格式无关。
   线长必须以「逐个字段累加」并与客户端的**长度校验**对齐（见 §4.3）。

3. **不确定就标 `?`，禁止编造。**
   任何字段不得留空、不得按「看起来像」猜。无法确证的一律写 `?` 并记入该命令的 `notes.md`。

## 3. 命令发现（INDEX 是怎么来的）

> 详细方法见 `_meta/命令发现方法.md`。这里只写规范要求。

3.1 **不允许手工拼凑命令表**。INDEX 必须由 `tools/ida_extract_commands.py` 从 exe 静态提取后生成，
以保证「命令全集」可信、可复现。

3.2 提取的三条机械判据：

1. 客户端把协议层函数名以字符串内联在代码里，形如
   `")->_proto_<类>_client::recv_<name>( "`、`")<-_proto_<类>_client::send_<name>( "`。
2. 引用该字符串的函数：
   - 一个函数内出现 **≥2 条** `recv_*` 名 → 该函数是 **S→C 分发器**（`switch(opcode)`）；
   - 一个函数内只有 **1 条** `send_*` 名 → 该函数是 **C→S 组包函数**。
3. **S→C 的 opcode**：反解分发器的 `switch` 实现（比较树 / 二级跳转表），
   得到 `opcode → case 块地址`；case 归属 = 「**不大于**该命令名字符串引用点的**最大** case 起始地址」。
   **C→S 的 opcode**：组包函数内 `mov word ptr [buf+0], IMM` 的 `IMM`。
4. **不经分发器的 recv**：单名字 `recv_` 函数（不是分发器）也能有命令 ——
   其 opcode 取该函数内 `movzx <r>, word ptr [...]` 之后紧邻的
   `cmp <16 位寄存器>, IMM`（`0x100 ≤ IMM ≤ 0xFFFF`）；
   **必须**同时确认它由分发器的**默认分支块**调用（否则视为未定位）。

3.3 已提取结果（2026-09-20，IDB `unpacked\GundamOnline_CHINA_v15.exe.i64`）：

| 协议类 | 分发器 | S→C 命令 | C→S 命令 |
|---|---|---|---|
| auth_client | `0xB03D30` | 8 | 8 |
| battle_client | `0xB0CC20` | 205 | 92 |
| lounge_client | `0xB51930` | 350 | 250 |
| **合计** | | **563** | **350** |

另有**不经分发器**的 recv：
- `_proto_battle::recv_entity_msma_fix` @`0xB0C210`（opcode **`0x20F5`**，由 battle 分发器的**默认分支块** `0xB31252` 调用）；
- `_proto_battle::send_entity_msma_fix` @`0xB0C910`（C→S，opcode 同为 `0x20F5`）计入 C→S。

⇒ **S→C 共 564、C→S 共 351，合计 915 条**，已全部登记进 `INDEX-命令总表.md`，opcode 无一条缺失。

3.4 每新增/修订一条命令，必须同步更新 `INDEX-命令总表.md` 的状态列，
并用 `tools/verify_index.py` 校验一致性。

## 4. C→S 分析规范（写线即真相）

C→S 的组包代码就在客户端里，**直接可见**，因此 C→S 的结论强度高于 S→C。

### 4.1 定位
`send_<name>` 函数（见 §3.2），地址记入该命令 `README.md` 的「代码位置」栏。

### 4.2 骨架提取（必须逐条记录）
按写线顺序，逐条记录写操作：

| 观察到的写法 | 含义 |
|---|---|
| `mov word ptr [buf+0], IMM` | 写 opcode（u16），`IMM` 即该命令的 opcode |
| `push IMM` + `call <分配器>` | 申请缓冲；`IMM` 是**容量**，不是线长 |
| `mov [p+k], reg` | 在偏移 `k` 写 4/2/1 字节（宽度由目标操作数判定） |
| `push imm` + `call <writer>` | 经写线助手写变长/嵌套字段，须追进该 writer |
| `cmp p, end` + `ja error` | 每次写入前的**边界检查**；成对出现说明该字段真实存在于线上 |

### 4.3 线长核算
把所有写入的字节数累加，得到「组包消费量」。

- 若与 `push IMM`（容量）不一致：**以组包消费量为准**，并在 `notes.md` 记录二者差值。
  - 容量是**预留上限**，只要求 `容量 ≥ 负载 + 2(opcode)`；实测常有富余（例：`0x20F5` 容量 `0x1A`=26，实际线长 13）。
- 若该命令存在对应的 S→C 应答，两边的字段表必须能互相解释（例如请求里的 id 会出现在应答里）。
  - 实测评据：`send_entity_msma_fix`(C→S) 与 `recv_entity_msma_fix`(S→C) 同为 `0x20F5`，
    两侧字段完全对称（5×u16 + u8 = 11 字节）——**双侧对称是强度很高的交叉验证**。

### 4.4 字段来源（用途）
对每个字段回答：**这个值是从哪儿来的？**
- 追 `reg` 的来源：对象成员 `[obj+K]`、栈上入参、全局变量、UI 控件取值；
- 字段用途必须落到「服务端据此做什么」或「客户端传它是为了什么」，并给出证据地址。

## 5. S→C 分析规范（消费即真相）

S→C 看不到组包代码，只能**从客户端的消费方式反推组包**。

### 5.1 定位消费点
用 INDEX 给出的 `case_start..case_end` 圈定该命令的处理块；块内即为消费代码。
（块内通常先打一条自身名字的 trace 字符串，可作为 `case` 归属的锚点。）

### 5.2 消费顺序 = 字段顺序
本客户端所有读取都经「读取器对象」的虚表方法（`[obj+0Ch]` 及其虚表项）：
- 每个读取前都有边界检查（`cmp 游标, 末尾` / `ja 出错`）；
- **读取顺序即线序**，不得按语义重排；
- 读到的值去向（写进哪个对象成员 / 喂给哪个 UI / 参与哪个判定）必须记录 —— 这就是字段用途。

### 5.3 长度校验（最强的收敛依据）
处理块末尾通常有「游标 == 报文末尾」的校验（或 `总长 == 累计消费量`）。
- **字段表的总长必须恰好等于该校验值**；不等则说明漏读/多读，必须继续找字段。
- 若找不到长度校验，线长只能标 `≥`，并在 `notes.md` 说明。

### 5.4 变长/重复字段
- 先读到 `count`/`len`，再驱动循环 → 记 `count` 的类型、上限检查、每元素字节数；
- 每元素字节数**必须**由循环里的步进判定（`add esi, N` / `lea edx, [eax+N]`），
  不得由结构体定义推断；
- 列表型成对命令（`*_begin` / `*_end`，如 `recv_*_list_get_r_begin` / `..._end`）
  必须在两份文档里互相链接，并说明分帧边界。

### 5.5 位域与压缩
出现 `shr`/`shl`/`and`/`bt`/`bts` 序列时按位域处理：记录**位宽、位序（先低位还是高位）、载体字节宽度**，
并写清它覆盖的是哪几个逻辑值。

## 6. 字段类型判定规范（强制汇编，禁止伪代码）

### 6.1 判定表（读侧 / 写侧）

| 读侧汇编 | 线类型 | 说明 |
|---|---|---|
| `movzx r, byte ptr [p]` | `u8` | 零扩展读 1 字节 |
| `movzx r, word ptr [p]` | `u16` | 零扩展读 2 字节 |
| `mov r, [p]` | `u32` | 读 4 字节 |
| `movsx r, byte ptr [p]` | `i8` | 符号扩展 |
| `movsx r, word ptr [p]` | `i16` | |
| `fld dword ptr [p]` / `movss` | `f32` | x87 / SSE 单精度 |
| `fld qword ptr [p]` / `movsd` | `f64` | 双精度 |
| `mov [p], ax` / `mov [p], al` | 写 `u16` / `u8` | 写侧宽度 |
| `rep movsb` + 长度前缀 | 变长字节串 | 长度前缀宽度单独判（见下） |
| 循环 + 固定步进 | 定长数组 | 元素大小 = 步进量 |

**长度前缀（字符串/字节串）** 必须单独判定前缀宽度：看前一个读取是 `byte` 还是 `word` 还是 `dword`。
字符串还要判编码（单字节 / UTF-16LE）：看是 `memcpy` 字节拷贝还是按 `word` 逐字拷贝。

### 6.2 高发错误清单（逐条自检）
1. **宽度混淆**：`u8` vs `u16` vs `u32` 必须逐个确认；同一字段在 C→S 与 S→C 可能宽度不同，不得互相套用。
2. **结构体偏移 ≠ 线体偏移**：`[obj+0x394]` 之类的成员偏移与报文字段偏移无关，严禁混用。
3. **容量 ≠ 长度**：`alloc(N)` / `add [ecx], N` 一律不当作线长。
4. **有符号 vs 无符号**：`movzx` 与 `movsx` 的区别就是有/无符号，别混。
5. **复用字段**：同一偏移在不同条件下含义不同（如 `union`），必须列出条件。

### 6.3 伪代码的正确用法
允许：用伪代码**找**消费点、**看清**控制流走向、**定位**被调用的子函数。
禁止：把伪代码里的变量类型、结构体字段类型直接抄进字段表。
规则：字段表里每一行的「线类型」都必须能指回一条**汇编指令地址**。

## 7. 字段含义与用途判定规范

每个字段必须同时给出**含义**与**用途**，且都有证据：

- **含义**（它是什么）：靠同函数内的字符串常量交叉引用 ——
  日志格式串（`push offset aXxx; push offset " (id:"`）、UI 字段名、枚举名。
- **用途**（它干什么）：
  读侧 → 追该值的去向（写入哪个对象成员 / 哪个 UI / 哪个判定分支）；
  写侧 → 追该值的来源（哪个对象成员 / 哪个 UI / 哪个开关）。
- 若确实无用途（仅回显、仅日志、仅占位），必须写「仅回显/仅日志」**并给出证据地址**，不得空白。
- 枚举字段：把枚举取值表列出（可取 `datatables/` 或客户端字符串表交叉验证），并标注来源。

### 7.1 字段表的强制列

| 列 | 要求 |
|---|---|
| 序号 | 线序，从 1 开始（opcode 记第 0 项） |
| 偏移 | 相对报文体（opcode 之后）的字节偏移；跨帧的标 `frame#` |
| 长度 | 字节数（位域用 `bit`，并给载体字节数） |
| 线类型 | §6 判定出的类型（`u8/u16/u32/i8/i16/f32/f64/bytes/array<T,N>/bitfield`） |
| 字段名 | 有原名用原名，无原名用 `f_<偏移>` 并标 `?` |
| 含义 | 一句话 |
| 用途 | 一句话；追到去向/来源 |
| 取值/枚举 | 范围或枚举表，或 `-` |
| 证据 | 汇编指令 VA（可多条，逗号分隔） |
| 置信度 | `确证` / `推测` / `未知` |

## 10.5 静态分析与资源证据来源

EXE 静态分析使用用户配置的正确 `ida-pro-mcp`（13338）访问 `GundamOnline_CHINA_v15.exe` 对应 IDB；记录 MCP、模块名、函数地址及必要的指令/数据流证据。不要改用 `gonline_ida_pro_mcp` 或自行从其它 EXE/dump 取代该 MCP 结论。若 MCP 当前无法解析目标，记录具体阻塞并继续可独立完成的工作，不从旧资源副本补证。

`unpacked/` 是早期解包/测试目录。目录内资源、数据表、脚本以及其中任何 `.unpackdat` 文件均不作为权威资源证据；目录中的 IDA 数据库仅因其通过上述 MCP 被用于 EXE 静态代码分析而可引用，不得把同目录其它文件当作旁证。正式资源证据只使用 `机动战士敢达Online/GundamOnline/unpackdat/` 中可复核的原始文件。正式目录缺少对应文件时，记录为“缺失/未验证”，不以早期副本填补。

## 11. 禁止事项

1. 禁止用伪代码的类型声明当字段线类型。
2. 禁止在客户端运行时挂调试器/下断点（反外挂会判死）；本分析**全程 IDA 静态**。
3. 禁止把「测试环境能跑通」当作结论依据。
4. 禁止编造字段、禁止把「未读到」写成「不存在」。
5. 禁止把容量、结构体大小当成线长。
6. 禁止脱离证据下结论；禁止以本目录以外的旧结论作为依据（本轮为全新分析）。

## 12. 工具与运行方式

| 工具 | 运行方式 | 作用 |
|---|---|---|
| `tools/ida_extract_commands.py` | IDA MCP：`py_exec_file` | 提取全部命令 → `_meta/commands_raw.json`（含伪 case 验证） |
| `tools/ida_draft_wire.py` | IDA MCP：`py_exec_file` | 逐条命令机械提取字段序列 → `draft-wire.md` / `draft-fields.csv` / `_meta/wire_draft.json` |
| `tools/ida_diag_cases.py` | IDA MCP：`py_exec_file` | 诊断 `case 块 ↔ opcode ↔ 名字` 三方对照 |
| `tools/build_index.py` | Python 3（stdlib） | 生成 `INDEX-命令总表.md` 与命令文件夹骨架 |
| `tools/verify_index.py` | Python 3（stdlib） | 校验 INDEX / 文件夹 / JSON 三者一致 |

工具本身也要遵守本规范：提取脚本只做**机械提取**，不做语义猜测。
