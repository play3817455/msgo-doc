## 2. 分析纪律（硬性）

1. **全程 IDA 静态**。不附加调试器、不在客户端下断点（软/硬件断点均被反外挂检测）。
2. **客户端只读**：不修改 exe、不改 `sysinfo.ini`、不 taskkill 客户端进程。
3. 本目录为**全新分析**：不以本目录以外的任何历史结论为依据。
4. 发现矛盾时保留原结论并追加「推翻依据 / 新结论 / 日期」，不直接删除。

| battle 特殊处理 | `0xB0C210` | `_proto_battle::recv_entity_msma_fix`（不经分发器；opcode **`0x20F5`**，函数内 `0xB0C256` 复检） |
| auth 跳转表 | 无 | auth 分发器全部由比较树实现 |
| battle 跳转表 | `jmp 0xB22835` | 字节表 `0xB317FC` → 目标表 `0xB317E0`，base `0x8D1F`，6 个真 case |
| lounge 跳转表 | `jmp 0xB605BD` 等 5 处 | base `0x5281` / `0x73F0` / `0xC9FA` / `0xD52A` / `0xEE0B`，各 4 个真 case |

跳转表的形态（MSVC 二级表）：

```asm
sub     eax, BASE            ; switch 表达式 = opcode - BASE
cmp     eax, MAXIDX
ja      default
movzx   eax, ds:byte_TBL[eax]   ; 字节表：索引 → 目标表下标
jmp     ds:JPT[eax*4]           ; 目标表：下标 → case 块地址
```

⇒ 真 case 的 opcode = `BASE + 表下标`；指向 `default` 的表项不是命令，必须剔除。

## 5. 命令名字符串的形态

客户端把协议层函数名以字符串内联在代码里（本轮发现方法的基础）：

```
")->_proto_lounge_client::recv_clan_rokaku_tree_get_r( "
")<-_proto_battle_client::send_entity_msma_fix( "
```

- `->` = 收到（服务端→客户端，S→C）
- `<-` = 发出（客户端→服务端，C→S）

每条例名字符串的引用点落在对应的处理函数/组包函数内部，可直接据此定位实现代码。

## 6. 坑：链尾的「伪 case」（`0x0A79` / `0xF0B0`）

比较树的链尾存在这种形态：

```asm
; VA: 0xB86084 .. 0xB8609C
0xB86084  sub     eax, 0F0B1h       ; 先减基准
0xB86089  jz      loc_B8632C        ; ⇒ opcode == 0xF0B1 是 case
0xB8608F  sub     eax, 19h          ; ← 这里曾被误记为一个 case（0xF0B0）
0xB86092  jnz     def_B605BD        ; ⇒ opcode == 0xF0CA 是 case
0xB86098  push    52h
0xB8609C  call    sub_B41120        ; ← 真正的 case 体起点
```

用「可能取值区间收窄」反解时，链尾会把区间收窄到 `(K-1, K-1)`，
而记录点用的是「续扫地址」⇒ 会把**判定指令**（`cmp`/`sub`）当成 case 体，产出伪 opcode。

**判据与处置**：区间收窄到单点时，必须用**具体值顺链走一遍**再决定是否登记：

- 按实际值判定 `jg/ja/jge/jl/jle/jz/jnz`；跟随 `jmp`；对跳转表按下标取目标；
- 途中遇到 switch 的 `default`（`si.defjump`）、`ret`、函数外 ⇒ **判否（伪 case）**；
- 落到「不属于比较链的指令」⇒ 判是（真 case 体）。

已剔除：`0x0A79`@`0xB54CDE`、`0xF0B0`@`0xB8608F`；对应真命令为
`0x0C41 recv_exchange_play_bonus_r`（体 `0xB54CF0`）与 `0xF0CA recv_chat_whisper_up_r`（体 `0xB8609C`）。

⇒ 三个分发器最终 **case 数 == 名字数**（8/8、205/205、350/350）。
复核工具：`tools/ida_diag_cases.py`。

## 7. 线格式读写原语（阶段二批量提取的基础，**已逐个看过函数体**）

客户端的字段读写全部走这几个小函数（`cursor` 结构统一为 `{ cur@+0, end@+4 }`）：

### 7.1 读侧

| 函数 | 宽度 | 边界检查 | 语义 |
|---|---|---|---|
| `sub_B02DD0` | 4 | 有（`cmp`+`jbe`） | 读 **u32** 并写入 dst；游标 +4 |
| `sub_B02DF0` | 2 | 有 | 读 **u16**；游标 +2 |
| `sub_B06230` | 1 | 有 | 读 **u8**；游标 +1 |
| `sub_B41470` / `sub_B413B0` / `sub_B05E30` | 4 / 2 / 1 | **无** | **只推进「解码缓冲」游标**（预留槽位并返回槽地址），真正的取值由随后的 bounded 读取器完成 |
| `sub_B41850` / `sub_B05E40` / `sub_B05EA0` | 4 / 2 / 1 | 无 | 定长**数组**预留（循环 N 次，`N` 由调用方给） |
| `sub_B02BA0`（及其同族） | 变长 | 有 | 读 **NUL 结尾字符串**：消费 = 串长 + 1；内部 `call sub_CC56B0`(memcpy) |

### 7.2 写侧（C→S）

| 函数 | 宽度 | 语义 |
|---|---|---|
| `sub_B02D80` | 4 | 写 **u32**；游标 +4 |
| `sub_B02DA0` | 2 | 写 **u16**；游标 +2 |
| `sub_B061C0` | 1 | 写 **u8**；游标 +1 |
| `sub_B02B40` | 变长 | 写字符串：内容 `edi` 字节 + **1 字节 NUL**（`edi = sub_C85E30(src, N)`） |

### 7.3 高频形态：`sub_B413B0` + `sub_B02DF0` 成对（**只算一个字段**）

```asm
0xB0D365  call sub_B413B0    ; 预留 2 字节解码缓冲槽 → var_1B2C 得到槽地址；var_1B14 += 2
0xB0D374  call sub_B02DF0    ; 从 wire 游标 var_1B28 读 u16 填进该槽（带边界检查）
0xB0D37C  test al, al
0xB0D380  jnz  ok            ; 成功分支是「跳转目标」，失败落在顺序里
```

⚠️ 两个坑（都会导致字段数错）：
1. **不要**把「预留」也算成一个字段 —— 一个字段 = 一次 bounded 读取；
2. 必须**跟成功分支**：`test al, al` 后若是 `jnz <ok>`，要跳到 `ok` 继续扫，
   否则会走进错误分支（`vt[0x64](1, 错误码)`）而提前结束。

### 7.4 三个「非 IO 但常出现」的调用（不是字段，见到不算停）

| 函数 | 语义 |
|---|---|
| `sub_ABB2F0` | 用传输层缓冲初始化 `{cur,end}` 游标 |
| `sub_CA0CE0` | 复位/清空一个临时游标或结构 |
| `sub_B02FF0` | C→S 的**提交/发送**（组包结束的标志） |
| `sub_B03020` / `sub_B05D90` / `sub_B41110` | 日志打印 / case 收尾 / 成员数组取值（**读窗口之外**） |

### 7.5 容量与线长的关系（**自校验用**）

| 方向 | 关系 | 说明 |
|---|---|---|
| S→C | `解码缓冲容量 == 负载字节数` | 小而定长的命令**精确相等**（已实测 325 条 `==`）；列表/变长型会更大（容量是上限） |
| C→S | `组包缓冲容量 ≥ 负载 + 2(opcode)` | 容量是**预留上限**，通常更宽（例：`0x20F5` 容量 `0x1A`=26，实际线长 13） |

判据：全定长命令若出现 **`Σ字段 > 容量`** ⇒ 一定多算了字段（重复计数）；
实测 915 条中 **0 条** 超容量（S→C PASS 429 / C→S PASS 229 / 含变长或数组 N/A 255）。
