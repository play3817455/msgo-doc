```
")<-_proto_<类>_client::send_<name>( "     ← 发出：C→S
```

按类统计：

| 类 | S→C（`recv_`） | C→S（`send_`） |

| `_proto_battle_client` | 205 | 92 |

| 其它（RTTI 类名、`RecvException` 等） | — | — |
| **合计** | **563** | **350** |

（另有 2 条不在 `_client` 命名空间下：`_proto_battle::recv_entity_msma_fix` @`0xB0C210`（opcode `0x20F5`）、

## 2. 名字 → 实现函数

对每条名字符串取 `XrefsTo`，落在哪一个函数里：

- 函数内出现 **≥2 条 `recv_*` 名** ⇒ 该函数是 **S→C 分发器**（`switch(opcode)`）；
- 函数内只有 **1 条 `send_*` 名** ⇒ 该函数是 **C→S 组包函数**。

一轮分组结果：915 条字符串落在 **355** 个函数里：

| 函数 | 大小 | 名字数 | 判定 |
|---|---|---|---|
| `sub_B03D30` | `0xF32` | 8 | auth S→C 分发器 |
| `sub_B0CC20` | `0x24BBF` | 205 | battle S→C 分发器 |
| `sub_B51930` | `0x377E6` | 350 | lounge S→C 分发器 |
| 其余 352 个 | — | 1 | 351 个 `send_*` 组包函数 + 1 个特殊 `recv_` |

⇒ 「一个组包函数 = 一条 C→S 命令」成立，**无需**再反解发送侧的分发逻辑。

## 3. S→C 的 opcode：反解分发器的 switch

分发器入口先取报文的第 1 个 u16 作为 opcode：

```asm
movzx   eax, word ptr [ebp+0]      ; opcode = *(u16*)buf
movzx   eax, ax
cmp     eax, 8F36h
jg      loc_B047D3                 ; 二分比较树
jz      loc_B04667
...
```

MSVC 对这种 `switch` 生成两种形态，**两种都要处理**：

### 形态 A：二分比较树（`cmp reg,K` + `jg/jz/jnz`）

特征：对同一个寄存器反复与立即数比较，`jg` 走「更大的一侧」，`jz` 命中一个 case，
最后一个用 `jnz`（不命中则跳默认）。

反解算法（`resolve_case_map`）：把「当前可能取值区间 `[lo,hi]`」随每次条件跳转收窄，
区间收到单点即为一个 case：

| 条件跳转 | 取一侧（taken） | 落空一侧（fallthrough） |
|---|---|---|
| `jg` / `ja` | `[K+1, hi]` | `[lo, K]` |
| `jge` / `jae` | `[K, hi]` | `[lo, K-1]` |
| `jl` / `jb` | `[lo, K-1]` | `[K, hi]` |
| `jle` / `jbe` | `[lo, K]` | `[K+1, hi]` |
| `jz` / `je` | `[K, K]` | `[lo,K-1] ∪ [K+1,hi]`（两条都继续走） |
| `jnz` / `jne` | `[lo,K-1] ∪ [K+1,hi]` | `[K, K]` |

注意两点（否则会漏 case）：
1. `cmp` 与 `jcc` 之间可能夹着**不改变标志位**的指令（如 `mov [esp+..], ebx`），必须跳过；
2. 扫描时不要因为途中出现 `retn` / `jmp` 就放弃 —— 序言里的提前返回分支之后才是比较树。

### 形态 B：二级跳转表（`sub` + 字节表 + 目标表）

```asm
sub     eax, 8D1Fh        ; switch 表达式 = opcode - BASE
cmp     eax, 0C5h
ja      def_B22835        ; 越界 → 默认
movzx   eax, ds:byte_B317FC[eax]   ; 字节表
jmp     ds:jpt_B22835[eax*4]       ; 目标表
```

- 真 case 的 opcode = `BASE + 表下标`；
- 目标表里指向 `default` 的表项**不是命令**，必须剔除；
- 该形态常出现在比较树的「默认分支」里（即默认分支又是一张表），因此需要**沿着默认分支继续反解**。

### 校验（形态 A 手工复核样例：auth 分发器）

| opcode | case 块 | 命令名 |
|---|---|---|
| `0x298E` | `0xB03DC8` | `recv_worldlist_get_r` |
| `0x1146` | `0xB04068` | `recv_worldlist_select_r` |
| `0x4F3F` | `0xB04355` | `recv_overplay_resettime_get_r` |
| `0x60E0` | `0xB044D6` | `recv_authenticate_you9otp_input` |
| `0x8F36` | `0xB04667` | `recv_authenticate_you9channeling_r` |

## 4. 名字 → opcode 的归属规则

case 块里会内联一句自己名字的 trace（`push offset aProtoAuthClien_10`），所以：

> **归属规则**：某条名字符串的引用点，归属于「**不大于**该引用点的**最大** case 起始地址」。

该规则在 auth（8/8）、battle（205/205）上完全命中。

## 5. C→S 的 opcode 与线长

组包函数骨架固定（样例 `send_proto_version_check @0xB04C70`）：

```asm
mov     ecx, [edi+0Ch]
mov     eax, [ecx]
mov     edx, [eax+78h]
push    0Eh                        ; ← 缓冲区容量（不是线长！）
call    edx
...
lea     ecx, [ebp+0Eh]
lea     eax, [ebp+2]
cmp     eax, ecx                   ; 边界检查
mov     word ptr [ebp+0], 34A9h    ; ← opcode 写在这里
ja      error
```

⇒ 提取规则：
- **opcode** = 函数内 `mov word ptr [buf+0], IMM` 的 `IMM`；
- **容量** = `push IMM` + `call <从 [obj+78h] 取出的分配器>` 的 `IMM`（记作「声明容量」，非线长）。

### 6.1 伪 case 的发现与剔除（`0x0A79` / `0xF0B0`）

区间收窄法初版曾在 lounge 多解出 2 个「无名 case」：

| 伪 opcode | 记录到的地址 | 该地址真实身份 |
|---|---|---|
| `0x0A79` | `0xB54CDE` | 链上的 `cmp eax, 0C41h`（**是判定，不是 case 体**） |
| `0xF0B0` | `0xB8608F` | 链上的 `sub eax, 19h`（**同上**） |

成因：比较链在链尾把可能取值区间收窄到 `(K-1, K-1)`，而记录点用的是「回到链上的续扫地址」，
于是把一个**判定指令**当成了 case 体。真实命令是这条链上的
`0x0C41`（`recv_exchange_play_bonus_r`，体 `0xB54CF0`）与
`0xF0CA`（`recv_chat_whisper_up_r`，体 `0xB8609C`）—— 这两条本来就已经正确解出。

**修正**：区间收窄到单点时，不再直接记录，而是用**具体值顺链走一遍**
（`concrete_ok()`：按实际值判定 `jg/jz/jnz`、跟随 `jmp`、解跳转表、遇 default/`ret` 即判否），
只有真的落到「不属于比较链的指令」（即 case 体）才登记。
修正后三个分发器 `case 数 == 名字数`，且 auth 的 8 条映射与人工复核表完全一致（未受影响）。

工具：`tools/ida_diag_cases.py` 可随时重跑这项对照（`case 块 ↔ opcode ↔ 名字`）。

### 6.3 不经分发器的 recv：opcode 怎么定（`0x20F5`）

`_proto_battle::recv_entity_msma_fix` 是**单名字函数**（不是分发器），所以不能靠 switch 反解。
两步定位：

1. **找调用者**：`sub_B0C210` 的唯一代码引用来自 `0xB31256`，落在 battle 分发器的
   **默认分支块** `0xB31252`（`jumptable 0xB22835` 的 default）。
   **实测校验**：用具体值模拟比较树 ⇒ `0x20F5` ⇒ `DEFJUMP 0xB31252`
   （对照组 `0x3CC` ⇒ `BODY 0xB0CD3B`、`0x8D1F` ⇒ 跳转表）。
2. **读函数内的复检**：`0xB0C253 movzx eax, word ptr [buf]` 之后紧跟
   `0xB0C256 cmp ax, 20F5h` ⇒ **opcode = `0x20F5`**。

⇒ 提取规则（已实现在 `scan_orphan_recv()`）：单名字 `recv_` 函数中，
`movzx <r>, word ptr [...]` 之后 10 条指令内出现 `cmp <16 位寄存器>, IMM`（`0x100 ≤ IMM ≤ 0xFFFF`）⇒ `IMM` 即 opcode。

**副产品**：发放两侧同号（`send_entity_msma_fix` 也是 `0x20F5`），是一条**双向同 opcode** 的命令；
客户端把它排除在 `_client` 的 switch 之外，改由默认分支做二级判定。

## 7. 阶段二：字段序列的批量机械提取（`tools/ida_draft_wire.py`）

命令全集定案后，逐条命令的**字段序列**也能批量机械提取，做法：

1. **先定 IO 原语表**（见 `环境与工具约定.md` §7）：读 3 个 + 写 3 个 + 变长串 1 个 + 预留/数组若干；
   识别方式是函数体形态（无 `call` + 唯一的 `add <mem>, IMM`），不靠地址写死。
2. **定位字段窗口**：从 `push 容量; call <[obj+78h] 的分配器>` 之后开始，
   到「非 IO 调用（日志/case 收尾）」或 `ret` 为止。
3. **按线序记账**：
   - `call <bounded 读/写原语>` ⇒ 一个字段，宽度 = 该原语的游标步进；
   - 内联 `movzx/movsx <r>, byte|word|dword ptr [<游标>]` ⇒ 一个字段；
     写侧内联 `mov [<游标>], <小寄存器>` ⇒ 宽度取寄存器宽度；
   - `call <变长串原语>` ⇒ 一个 `bytes` 字段（长度动态，此前偏移链停止累计）。
4. **跟成功分支**：`test al, al` 后若为 `jnz <ok>`，跳到 `ok` 继续扫（否则会走进错误上报而提前结束）。
5. **自校验**：全定长命令必须满足 `S→C 容量 == 负载长`、`C→S 容量 ≥ 负载长 + 2`；
   出现 `Σ字段 > 容量` 即判定为重复计数。

首轮结果（913 条草案）：

| 方向 | 条数 | 自校验 PASS | FAIL | N/A（含变长/数组） | 平均字段数 |
|---|---|---|---|---|---|
| S→C | 564 | 429 | **0** | 133 | 2.9 |
| C→S | 351 | 229 | **0** | 122 | 2.4 |

**0 条超容量** ⇒ 没有重复计数；`PASS` 里 325 条是 `容量 == 负载长` 的**强相等**证据。
草案的「类型/偏移/长度/证据」已可直接采信，**「含义/用途」仍需人工补齐**（故状态记为 `DRAFT`）。
