## 2. 反例 / 易错点（★本批重点）

- **机器草案严重漏读**：草案只抽到 2 个字段（`ent_id`/计数），在 `0xB10734 call sub_B06090`（数组预留）处**停止扫描**，把整个 `parts_exec` 数组（N×6 个子字段）漏掉。⇒ 必须人工续扫「计数 + 数组 + 尾字段」。
- **结构体槽步进 ≠ 元素线长**：缓冲步进 `0x14 = 20`（`sub_B06090` 的 `add [edx],14h` 与循环 `add [var_1B2C],14h`），而元素读取器 `sub_B06CF0` 实际只消费 **17** 字节（`4+4+1+2+4+2`）⇒ **容量按 20/槽记账**，`0x2086 = 2 + 4 + 416×20`。若按 17 算会得 `7078 ≠ 8326`。
- **元素读取器是「有 `call` 的原语型」但尾字段在成功路径上**：`sub_B06CF0` 在 `0xB06D54 loc_B06D54` 有失败出口 `retn`，**成功路径从 `0xB06D5D` 继续**再读 `[edi+0x10]` 的 u16（`sub_B02DF0`）⇒ 只扫到第一个 `retn` 会把元素线长误判为 15。**必须整函数扫描**（`sub_B06CF0` = `0xB06CF0..0xB06D71`）。
- 三个「预留」调用（`sub_B413B0`、`sub_B06090`）**都不是字段**；字段 = 每次 bounded 读（`sub_B02DF0`/`sub_B02DD0`/`sub_B06230`）或元素读取器内的一次内联读。
- 数组**没有**独立「没有元素时跳过循环」的额外字段：N == 0 时数组占 0 字节，尾部闭合校验随之成立。
