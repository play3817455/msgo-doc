## 追加：消费端全链取证 ⇒ 这是「服务端委派的命中解算」下行（2026-09-30）

**线格式不变**（§3 的 3 字段 `ent_id(u16)` / `weapon_itemid(u32)` / `fire_id(u32)`、线长 10、容量 0xa 全部仍成立），
本追加只补**语义与收件集**。

### 1. 分发 → 业务：逐环已钉死

vftable = `CGVOProtoBattle` 基址 `0xEED7AC`（与受击反应族的 `vt[0x1FC..0x208]` 同一张表）。

| 环 | 证据 |
|---|---|
| 分发器 case 块 → `vt[0x1D0]`（3 实参） | 本 README §1（块 `0xB2F913..0xB2FB4A`，去向 `0xB2FB2E`） |
| `vt[0x1D0]` == `sub_BA9DA0` | vftable 直读 `[0xEED7AC+0x1D0] = 0xBA9DA0` |
| `sub_BA9DA0` 转发 → `sub_AFDCD0`，`retn 0Ch` | `sub_AFDCD0`（3 实参配平） |
| `sub_AFDCD0` → `sub_517D50` | `0xAFDD9E`。`sub_517D50` 的**全部**调用者只有两处：本处 + `sub_4E0D50@0x4E0FDF`（本机侧范围解算入口，`sub_4E0D50` 本身只被虚表数据 `0xD71E30` 引用） |

### 2. `sub_AFDCD0(ent, weapon_itemid, fire_id)` 的动作（伪代码逐句）

1. **门**：`(*(_BYTE*)(*a1 + 0x440) & 1) == 0` 才继续（该字节 bit0 也是転倒起身链 `sub_501270`
   读的同一判位，见《战斗模型推导报告》§6.3.7④；它在本 build 内没有名称层证据 ⇒ 见 §3 新增存疑）；
2. 用 `weapon_itemid` 查武器参数（`sub_4317D0(dword_11E3F08+4, …)`），取描述符 `*(param+2576)`，
   读 byte `+25`（= 该参数有 **`EXP_RANGE`** 那一格）与 float `+28`（= `EXP_RANGE` 值）；
3. `sub_517D50(ent, fire_id, weapon_itemid, EXP_RANGE)`。

`sub_517D50(a1=实体, a2=fire_id, a3=weapon_itemid, a4=半径)`：
清零 284B 暂存区 `dword_11EB810` → `sub_5173F0(…, sub_517AF0)`（遍历实体表 + 包围球 + `EXP_RANGE` + 视线校，
逐目标写暂存区）→ 按 `sub_474B90(*a1)` 二选一发出 **`CS-0x770D`（完整，`sub_B028D0`）**
或 **`CS-0xA8FE`（短格式，`sub_B02460`）**，`a3`/`a2` 直通为 `weapon_itemid`/`fire_id`。

### 3. 结论

- **语义**：本命令 = **服务端把「某实体的一次 `destruct` 范围武器，爆点就在该实体上」交给客户端本地解算并回报**。
  客户端**不解算任何伤害**，只做「谁被挂到」的判定 + 测距，然后把 **`fire_id` 原样照抄**回 `CS-0x770D`/`CS-0xA8FE`。
- **收件集**：解算不能重复 ⇒ **单播给该实体的属主会话**（`entity+12` bit0 = 本机拥有位，
  见 `sub_5173F0` 开头：自机时上报的 `AI_ent_id` 位置写 0）。**不是全房广播**（同族 `SC-0x747B` 才是广播）。
- **链路闭合**：`CS-0xA8FE` 此前只追到「唯一生产者在 `sub_517D50` 的短格式分支」；
  本追加拿到了 `sub_517D50` 的**全部上游**（本机开火 `sub_4E0D50` / 本命令 `sub_AFDCD0` /
  `SC-0x747B` 的 `sub_518940`）⇒ 三条路共用同一个上报器与同一块暂存区。

## 追加：门所读的 `entity+0x440` bit0 = 「搭乗/アクセス中」フラグ（2026-09-30，闭环 A1）

**结论**：`sub_AFDCD0` 第 1 句读的那个位**不是**「死亡/无敌/属主」之类的通用状态，
而是**乗降（アクセス）族专用的一位**：**置位 = 该实体正处于「搭乗/アクセス」关系中**。

### 1. 写入点全表（`find_bytes` 扫 `40 04 00 00` 位移字节 + 逐点反编译复核）

| # | 写入点 | 触发场景 | 动作 |
|---|---|---|---|
| ① | `sub_4B9EA0` | `SC-0x1B32 rideable_msma_ride` 的 `access_type == 11` 半（`vt[0x314]`=`sub_BAA910` → `sub_AFC9F0` → `sub_4BEF10` → `sub_4B9EA0`） | 命中实体 `*(*v7+1088) \|= 1`；**同一函数内相方实体** `*(*v9+1088) &= ~1` |
| ② | `sub_4BA4E0` | `SC-0x4C36 rideable_msma_get_down_r` 的 `access_type == 11` 半（`vt[0x318]`=`sub_BAA950` → `sub_AFCA40` → `sub_4BEF70` → `sub_4BA4E0`） | 同上形状：命中实体 `\|= 1` + 相方 `&= ~1`（本地/远端两半都在 `sub_4BEF70` 的 `a2==11` 里） |
| ③ | `sub_4C2D20` | 出現/生成（`a3 != 3 && (a3 & 2) != 0` 分支） | `*(*v46+1088) \|= 1`（＝「乗った状態で出現」の復元） |
| ④ | `sub_4BDD90` | `SC-0x1B32` 的 `access_type == 12` 半 | 命中实体 `*(*v10+1088) &= ~1`；同赠 `*(*v10+1960) = 1`、`*(*v10+12) = 0x20000`；另 `*(*v8+1088) &= ~8`（清 **bit3**，非 bit0） |
| ⑤ | `sub_4BE190` | `SC-0x4C36` 的 `access_type == 12` 半 | `*(ent+1960) = 0`（**不动 bit0**） |
| ⑥ | `sub_4C04E0` | 生成 / 再出現 / 配備完了 | `*(*a3+1088) &= ~1` |

⇒ **写入侧只有乗降族**（`SC-0x1B32`/`SC-0x4C36` 的 `access_type ∈ {11, 12}`）+ 生成族（`sub_4C2D20`/`sub_4C04E0`）两类，
没有任何 HP/死亡/属主路径写它。

### 2. 读取点全表

| 读取点 | 判据 | 效果 |
|---|---|---|
| **本命令 `sub_AFDCD0`** | `(*(_BYTE*)(*ent+0x440) & 1) == 0` 才继续 | 置位 ⇒ **本命令不做任何事**（不解算 `EXP_RANGE`） |
| `sub_501270`（`0x4000` 転倒進入，§6.3.7④） | `(*(_BYTE*)(*(this+1)+1088) & 1) != 0` | 置位 ⇒ `this[3] = sub_4FE700`（**跳过常规起身链**） |
| `sub_4F5F30` | `(*(_BYTE*)(*(this+1)+1088) & 1) == 0` 才 `(*(this+1192))(this, a2, 0)` | 置位 ⇒ **不跑自身移動更新** |
| `sub_4ED310` | 读/写**同一字节的 bit1**（`^(2*v2) & 2`），由 `move+0x1099` 计数器跨 0 时 toggle | ⇒ 证明 `+0x440` 里 **bit0 与 bit1 是两个互不相同的独立位**（bit1 = 反応モード），不会与本位混用 |

### 3. 为何这不是「死亡」之类的通用位

三个读取点合起来的语义是同一句话：**「正在搭乗/アクセス中的实体，不自已跑移動更新、不做起身演出、不自己解算爆風範囲」**
（＝自分の位置・姿勢・解算を親＝乗せている側に任せる）。
这与写入侧「乗降族 + 生成時の復元」完全互洽；而 HP 归零/撃破那一族的落点是
`move+0x154/0x158` 的**動作モードフラグ**（§6.3.7①②）与 `move+0x14` 的 `0x40000` 系**状態値**（§6.2.7），
与本位无交集。
