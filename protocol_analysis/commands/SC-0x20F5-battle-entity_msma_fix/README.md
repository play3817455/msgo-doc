## 2. 结论摘要

- **报文体总长：`13` 字节**（opcode `2` + 负载 `11`）。
- 负载 = **5 × `u16` + 1 × `u8`**。
- 长度校验：`0xB0C37C cmp ebx, [esp+58h+var_2C]` + `jnz 错误`（`0xB0C380`）——
  要求**读完后游标 == 报文末尾**，故负载恰好 11 字节。
- 是否分帧：否。
- 关键结论：**双向同 opcode** 的一条「实体/机体修正」命令；客户端把 5 个 u16 + 1 个 u8
  解析后一次性交给 `vt[0x68]` 应用（`0xB0C542`）。
- **为什么它不在分发器的 switch 里**：`0x20F5` 走比较树/跳转表都会落到 default
  （实测：`walk(0x20F5)` ⇒ `DEFJUMP 0xB31252`），该默认块把未识别 opcode 交给
  `sub_B0C210` 再判定一次，形成「二级处理」。

## 4. 分析记录

### 4.1 定位过程
1. 名字符串 `0xEDC0D4` 的 xref `0xB0C3A4` 落在 `sub_B0C210`（单名字函数 ⇒ 不是分发器）。
2. `sub_B0C210` 的唯一代码引用来自 `0xB31256`，位于 battle 分发器的**默认分支块** `0xB31252`。
3. 用具体值模拟 battle 分发器比较树：`0x20F5` ⇒ `DEFJUMP 0xB31252`（**已实测**），
   与「默认块调用本函数」一致；块内 `0xB0C256` 再次 `cmp ax, 20F5h` 完成判定。

### 4.2 长度闭合
- 读取序列：1 次内联 `u16` + 4 次 `sub_B02DF0`(u16) + 1 次 `sub_B06230`(u8)
  = `2*5 + 1` = **11 字节**。
- 读完立即校验 `游标 == 末尾`（`0xB0C37C`/`0xB0C380`）⇒ 与 11 字节自洽 ✓。
- 交叉印证：解码缓冲容量 `push 0Bh`（`0xB0C29D` ⇒ `vt[0x78]`）= **11**，与负载字节数相等。
  （按规范 §4.3，容量**只作旁证**，线长仍以消费量为准。）

- 见 `notes.md`（6 个字段的**含义**未定：当前只确证了类型与位置）。
