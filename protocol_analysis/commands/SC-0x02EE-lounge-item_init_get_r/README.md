## 2. 结论摘要

- **报文体总长：变长**（含 4 个「计数 + 元素数组」列表）。定长骨架 = `4×u16 + 6×u32 + 4×u32 + 4×u32 = 8 + 24 + 16 + 16 = 64` 字节，再加上 4 个列表的 `N × 22` 字节。
- 负载 = 4 个槽位数（`slot_num_*`）+ 6 个排序时间戳 + **4 组「计数 + 物品列表」** + 4 个「计划排序」尾字段。
- 长度校验：`0xB529A2 mov ecx,[esp+2C5Ch+var_2C44]`、`0xB529A6 cmp ecx,[esp+2C5Ch+var_2C40]`（vs 报文末尾）、`0xB529AC jz ok`（不等 ⇒ `push 140h` 报错）⇒ **整包（含变长列表）必须精确消费完**。
- 声明容量 `push 0F400h`（`0xB52512`）= `62464`，是列表上限场景下的**缓冲上限**（`4×4 + (300+100+1300+900)×24` 量级；容量 ≠ 线长，见规范 §1 铁律 2）。
- 是否分帧：否。
- **每个列表元素线长 = `22` 字节**（由元素读取器 `sub_B434F0` 的实际消费量判定：`8 + 4 + 4 + 4 + 2`），
  而**解码缓冲中的元素步进是 `0x18`=24**（`sub_B416C0` 的 `add dword ptr [edx], 18h` 与各循环 `add ..., 18h`）——
  两者差值 2 字节是内存结构体对齐填充，**不是线上字节**（规范 §6.2 规则 2：结构体偏移 ≠ 线体偏移）。
- 关键结论：**物品栏初始化全量下发**（主/消耗/垃圾/计划 四类物品列表 + 排序时间戳 + 排序开关），
  18 组逻辑值一次性交 `vt[0x32C]`（`0xB52F59`）。
