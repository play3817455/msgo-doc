## 2026-10-11 客户端消费端补证

正确 v15 客户端中，SC `0x02D8` 分发到接收槽 `vt[0x2F4]`，实现路径为 `sub_BAA7B0 → sub_AFC840 → sub_68D820 + sub_6319C0`。`sub_68D820(ent_id,result)` 以回包参数操作一棵有序待处理容器，按参数键定位并移除对应范围，然后查找 UI 控件键 161 并调用控件方法；`sub_6319C0(ent_id,result)` 以首参数查客户端运行实体，并根据实体状态选择 1–4 档提示效果。

这证明响应不仅是空回执，也会清理客户端待处理状态、刷新 UI 并显示状态提示；但没有证据表明该路径直接增加阵营能量、物资库存或服务端战术条。协议字段 `result` 仍不能按名字解释为成功码，响应 `ent_id` 虽用于实体查找，也不能据此断言它就是待回收货柜 ID。服务端尚无可信容器账和奖励规则，因此不得仅凭客户端提示实现奖励。

证据锚点：`unpacked/GundamOnline_CHINA_v15.exe.i64` 的正确 v15 IDB；parser `0xB0D137..0xB0D320`，`sub_BAA7B0 @ 0xBAA7B0`、`sub_AFC840 @ 0xAFC840`、`sub_68D820 @ 0x68D820`、`sub_68D460 @ 0x68D460`、`sub_6319C0 @ 0x6319C0`。完整分支边界见 `serverv/docs/R001-地图玩法对象链.md` 的“0x02D8 回包消费端首轮闭合”。

## 2026-10-11 追加校正：ent_id是回收者待处理键

原结论：Q2及首轮笔记无法区分回收者与被回收对象。推翻依据：正确v15 `68D580 @68D7AF..68D7CA`读取本地自机handle所指actor的+4实体号，插入回收管理器+8的集合，只有新插入才发送6FA1；`AFC840`把回包首字段符号扩展为32位传入`68D820`，后者在同一管理器+8调用`68D460`，按该键求equal_range并删除。新结论：正常匹配该流程的02D8.ent_id必须是发起回收者实体号，不能填写设施或货柜实体号。

`6319C0`指令另证实result非0时跳过提示分支，result=0时才查该实体、要求actor mask bit1并按本地量表比例选择1–4档提示。此结果可确认客户端零值分支，仍未证明任何服务端资源奖励。反编译char参数/指针类型不可靠，字段宽度及this来源以指令为准。raw证据见serverv/docs/data/ida-v15-container-collect-gates-20261011.json。
