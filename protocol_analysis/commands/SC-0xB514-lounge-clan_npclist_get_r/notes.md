## 展示侧语义（2026-09-25 补，接 `CS-0xF4E7` 时取证）

- **三组是平行的**：6 个字段在 `B74851`..`B74878` 一次性经 `vt[0x41C]` 交给展示侧
  （6 实参 = 三组 ptr/count）⇒ `npclist_is_ex[i]` / `npclist_unlock_lv[i]` 与 `npclist_id[i]`
  是同一条军官的三个属性，**三组 count 应等长**。
- **`npclist_id` 是过场立绘 NPC id**：`0xB514` 的 case 块 `0xB74471`..`0xB748C2` ∈ lounge 的 S→C
  **巨型分发函数** `sub_B51930`（`0xB51930`..`0xB89116`，222KB 一个 switch —— INDEX 里几十条 SC 的块
  都挂在它名下，别当"这条命令的 handler"读）。处理块把每个 id 过 `CCutInNpcTable`
  （`TIndexTable<CUTIN_NPC_DATA>`：构造 `sub_A72A10`、取用点 `sub_A76810`、虚拟访问器 `sub_A80EF0`
  @ 数据槽 `0xECE868`）取行，再用行里的**图像 id** 去客户端本地的 `npc_rect.csv` 取矩形 ——
  该表里有 `部隊画面:上官` / `部隊作成:上官` / `部隊長選択:上官` 三组（这就是"军官"在界面上的样子）。
- **两张表都不在下载表里**：`cutin_npc.csv`（`カットインNPCID` 5 位 → `イメージID` 4 位）与
  `npc_rect.csv` 位于客户端 `settings/`（`download_list.csv` 的 npc 分组只有 `ai_param`/
  `ai_weaponparam`）⇒ **服务端没有这张表**，`npclist_id` 对服务端是**不透明 id**，只能原样回显。
- **上限 24 的来由**：三处 `cmp ebx,18h`；解码缓冲 `0x9C`=156 精确等于"三组各 24"的线长；
  块末 `B74637` 闭合（游标 == 报文末尾）⇒ 多发/少发都整包丢。
- **应答没有 `result` 字段** ⇒ 服务端无法表达"拒绝"，只能回空名录（`-13001`/`-10053` 那套在这里
  没有落点）。本仓库落地见 `serverv/internal/lounge/clan_npc_list.go`。

## ★ 名录 vs 名册：UI 布局已定性为**可选名录**（2026-09-25 补）

`layout.xml` 里两个窗口把这条链的语义钉住了（`str_table.txt` 解出中文标题）：

| 窗口 | 标题 | 内容 |
|---|---|---|
| `L07_ManageOfficer` | `82,7,70` = **长官变更** | `REF 6500` = `Ref_L07_OfficerSlotPage`：**一页军官槽**（`Ref_L07_OfficerSlot` = ID 6400：立绘 132×124 + 名字）＋**滚动条**（`REF 1023`）＋页码 TEXT 6503 ＋ **上一页/下一页**按钮（`7637`/`7641`）⇒ **可翻页的名录表格** |
| `L07_OfficerChange` | `82,7,70` = **长官变更** | `REF 6400` = **单个** `Ref_L07_OfficerSlot`（只画被选中的那一位）＋按钮 `84,1,4` **确定** / `84,1,25` **返回** ⇒ **确认框** |

⇒ 流程是「在**翻页名录**里挑一个 → 确认框里看那一位的立绘 → 确定」。**这是"可选名录"，不是"本族名册"**
（名册读法只需要一个槽，用不上滚动条 + 翻页 + 确认框）。
⇒ 顺带：名录**一次发全**（≤24 条），客户端自己分页 —— 这也解释了为什么上限是"解码缓冲 3×24"而不是
"一页的槽数"。

⚠ 因此本服现在的行为（只回首发的 `game.clan.npc_id`）会让"长官变更"界面里**只有 1 个候选**：
它**不撒谎、不自造 id**，但玩家换不了人 —— 名录数据（发哪 24 个 / `is_ex` / `unlock_lv`）**仍是欠账**，
且现在已知**必须**补齐才能真正可用。接缝仍只在 `clanNpcListEntries`（见 `clan_npc_list.go`）。
`is_ex`（`拡張`？）与 `unlock_lv` 的具体含义仍未取证。
