# 未决问题 / 反例 / 关联 —— SC-0x1FC7-lounge-clan_msgboard_news_get_r

## 1. 本命令要点

- 机器草案只抽到 2 个 u32 就止步于 `sub_B417D0`（248/槽数组预留），漏掉整个 `news` 数组与尾字段 `clan_kind`。
- 容量 `0xE91 = 3729 = 4 + 4 + 15×248 + 1` ⇒ 条目数上限 **15**（容量反推）。注意这是**落地槽口径**：`0xE91` 是解码缓冲的声明容量，按槽 248 记；线上元素只有 244，故线上限 `4 + 4 + 15×244 + 1 = 0xE55`（见 §2 第 3 项）。
- 元素线长 **244** = `sub_B45D20` 消费量 8+4+2+2+2+193+4+4+25（`body` 串长度取读取器循环上界 `0xC1`=193）。
- 元素内存跨度 **245**、槽步进 **248**、`news` 数组槽内均有填充 —— 线上字节数三者互不相等，见 §2。

## 2. 已定案（原「差 1 未定案」的收口）

| # | 项 | 结论 | 证据 |
|---|---|---|---|
| 1 | 元素线长 | **244**（草稿曾记 242） | 读取器 `sub_B45D20` 逐字段消费 244B（9 个写入点 @ `0xB45D3A`..`0xB45DFC`，无分支跳读）；草稿 242 = 漏计 `kind`/`nice_count`/`child_count` 三个 u16 中的一个（+0Ch/+0Eh/+10h 只算了两个） |
| 2 | 槽步进 | **248**（0xF8），与线长无关 | 数组预留 `0xB5824D call sub_B417D0`（push N）；数组循环 `0xB58276 add var_2C48,0F8h` |
| 3 | 声明容量 | `0xE91 = 4+4+15×248+1`，槽口径 | `0xB581A2 push 0E91h`；按线长算是 `0xE55`，两者不矛盾 |
| 4 | **「193 vs 194」** | **两者都对，量的不是同一件事**：线上 193（读取器循环上界 `cmp eax,0C1h` @ `0xB45DB8`，起点 `[edi+12h]`）；内存 194 是「`body` 末字节 → `pilot_id` 首字节」的偏移差（打印器 `[edi+12h]` → `[edi+0D4h]`） | `0xC1`=193；`18 + 193 = 211` 不是 4 的倍数 ⇒ `pilot_id`（u32）对齐到内存 212（0xD4），中间 **1B 自然对齐填充**。填充在**内存槽**里，不在线上：读取器自己也用 `[edi+0D4h]` 寻址，所以「193 线宽 + 1B 槽内填充 = 194 内存跨度」 |
| 5 | 元素内存跨度 | **245**（`name` 结束于 220+25=245）⇒ 槽 248 还含 **3B 尾部填充** | 打印器 `name` 起点 `[edi+0DCh]`=220（`add edi,0DCh` @ `0xB4EA5E`）；245 → 8 字节对齐 = 248 |

> 范例记法（本库口径）：**线宽只看读取器消费量**，内存偏移只用于解释槽尺寸；二者不等时一律写成「线宽 N + 槽内 k 字节填充（对齐/尾部）」，不再记成「未定案」。
