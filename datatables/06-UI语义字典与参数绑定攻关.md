## 六、★续攻（2026-09-14 晚）——一条工具坑 + 关键结构定案

### 6.1 ⚠️ 工具坑（**重要，别再踩**）：`ida_bytes.find_bytes` 在本环境**假阴性**

- 现象：`ida_bytes.find_bytes('4C30335F', …)`（想搜 ASCII `L03_`）返回空，**连已知存在的字符串都搜不到**；
  换 `bytes.fromhex('4C30335F')` 仍然空。
- 根因两条：① 该 MCP 环境里 `find_bytes` 不可靠（返回值恒空）；② `L03_MsParameterSlot` 在 exe 里是 **UTF-16LE**
  （实测 `get_bytes(0xe0ce04,6) = 4c 00 30 00 33 00` = `L\0 0\0 3\0`）。
- **正确做法 = 手工扫段**（已验证可用）：
  ```python
  for seg in idautils.Segments():
      st, en = idc.get_segm_start(seg), idc.get_segm_end(seg)
      blob = ida_bytes.get_bytes(st, en-st)          # 段别太大
      i = blob.find(bytes.fromhex('6A2A'))           # 用 bytes，不要用 str
  ```
- **推翻此前的错误结论**：§一"已排除错路②"里"**全 exe 无 `push 42`**"是**假阴性**——手工扫段实测 `6A2A` = **77 处**
  ⇒ 「(60,42) 无代码引用」这条**作废**。（仍然成立的部分：键常量 `0x003C2Axx` 与布局控件 `ID` 均未以常量形态出现。）

### 6.2 ★面板参数值的结构定案

- 面板把 6 个参数值存成 **`__int16` 数组：`panel + 1008 + 2*idx`**（idx 0..5），并调 `sub_61F5A0(idx, value)` 触发刷新。
  实证：`sub_61FAE0` 里 `*(_WORD *)(*v13 + 2*v15 + 1008) = v14;` 紧接着 `sub_61F5A0(v15, v20)`（`v15=idx, v14/v20=value`）。

  （都在 `0x61FAE0..0x6207D0`，各 0xf6~0x1f2 字节）。它们把 **`(idx, value)` 经"消息"**送进面板
  （`sub_61FAE0` 的入参 `a9=idx, a10=value` ⇒ 典型的消息分发形态）。

## 七、★★ 最后一跳完成（2026-09-14）：绑定函数 = `sub_61C9A0`

### 7.1 定位过程

- 6 个 setter（`0x61FAE0…0x6205E0`）各只有 1 个外部调用者，是一组**10 参透传 thunk**（`sub_AF94E0…`、`sub_BAC3F0…`），
  而 thunk 被**数据表**引用（`0xEEDE20..0xEEDE40`、`0xEEE128..0xEEE138`，形如 `{id, fn}` 的处理器数组）
  ⇒ **值经"消息"传入面板**：`sub_AF94E0` → setter → `panel+1008+2*idx = value`。
- 用**手工扫段**（`find_bytes` 不可用）扫 `disp32=0x3F0`（= +1008），命中 40 处；其中：
  - `sub_61C9A0` @`0x61cadd`：`movsx ecx, word ptr [ebp+edi*2+3F0h]` + **jumptable** ⇒ **按参数索引分派** ★就是它★
  - `sub_6182C0` @`0x6182ca`：`cmp word ptr [ecx+edx*2+3F0h], 3E8h`（参数值与 1000 比较）
