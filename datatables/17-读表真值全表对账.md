# 17 读表真值全表对账（Unicorn 仿真 vs schema vs 下发 CSV）

> 复现：`python datatables/_emu_readers.py` → `_emu_datadep.py` → `_sweep_verdict.py` → `_sweep_width_db.py` → `_sweep_report.py`

## 0. 方法与口径

1. **真值来源**：Unicorn 32 位跑 `GundamOnline_CHINA_v15.exe` 里 77 个 cfg 逐行读表函数，
   钩住四个 CSV 取列助手（`sub_BBB370` int / `sub_BBB470` float / `sub_BBB4F0`、`sub_456D90` 字符串）
   与枚举转换器，把列号换成唯一标记值再记录 `(写偏移, 标记)` ⇒ 列号来自**真实执行**，
   绕开静态常量传播（可穿透循环展开/指针差技巧）。
2. **静态交叉验证**：`_reader_pushconsts.py` 抽调用点前压栈的立即数列号，与仿真逐条比对一致：
   `sub_58C440`(PLAY_BONUS_REWARD) = `0,1,2,3,4,5,6,7,9`（跳列 8、读列 9）。
3. **越界列语义**（决定危害等级）：`sub_456D90` 反编译
   `if (a3 < (this[29]-this[28])/28) 取该列 else 输出空串` ⇒ **列号 ≥ 行宽 → 空串 → atoi/atof = 0**：
   不崩、不读脏数据；「我们 CSV 比 reader 读的窄」= **这些字段恒为 0（数值缺失）**。
4. **下发链路**：客户端拿到的 CSV = `meta.cfg_manifest.raw_csv`（`cfg.DBStore.ReadFile` 原样下发）；
   GM 改行后 `SyncTableManifest` → `ExportTableRawCSV` 按 `cfg.{表}` **物理列重拼** ⇒ 
   「DB 列数」与「raw_csv 行宽」都必须 ≥ reader 读到的列数。
5. **「读列数是否依赖数据」实验**（`_emu_datadep.py`）：把所有字符串列改回**空串**再跑一遍，
   与返回标记串相比 —— **74/77 个 reader 读集完全不变**（读列数是硬编码的），
   只有 `QUEST`/`ITEM` 变化（它们本来就在仿真失败名单里）⇒ §2/§3 的「读到的列数」是真值，
   不是「读到空列为止」的假象。
6. **结构性佐证**（IDA 反编译，可逐条复查）：
   - `sub_56EA00` AI_PARAM：列游标 `v36` **按引用**传给 `sub_56E890`(吃 5 列)/`sub_56E220`(每块吃 25 列，
     `(*a4)++` 逐个前移)/`sub_56E3F0`(吃 4 列)，三块带 + 头尾 ⇒ 总列数 **127，与数据无关**。
   - `sub_59E170` MISSION_EXTRULE：`v11=6; do{4 列}while(--v13); while(--v23=2)` ⇒ 固定 8 列（列 6..13）。

## A.1 原则（用户裁定）

**按客户端行为补；没有原版数据就自行占位。** 依据 `sub_456D90`（本次重新反编译复核）：

```c
v4 = this[28];                                            // 行字段数组（每字段 28 字节）
if (v4 && idx < (this[29] - v4) / 28) v5 = v4 + 28*idx;   // 界内 → 指向该列
else { sub_402AD0(&String, 0); v5 = &empty; }             // 越界 → 空串
*(dst + 20) = 0;                                          // 目标串长度 0
sub_4029E0(dst, v5, 0, -1);
```

⇒ **「越界列」与「存在但为空」的列对客户端完全等价**（两者都得到 `""` ⇒ `atoi`/`atof` = 0）。
所以补空列**不改变任何客户端行为**，换来三件事：

1. 列位诚实（库/CSV 宽度 == reader 读列数，不再依赖越界兜底）；
2. 库结构不再"少一截"（GM/审计不再报窄）；
3. 将来拿到原版数值可直接落库生效 —— **缺列时那些值是会被静默丢掉的**。

- 我们把 schema/库/种子统一声明为**上界 43 列**，保证 CSV 行宽稳定；写数据时**必须同时写 `csv2`**
  （只填机体槽而不写 `csv2`，客户端一个槽都不读）。这条已写进列注释与种子注记。
- 旧名 `pick_count` → `ban_ms_count`（它是**条数**，不是"可选机体数"）；`ban_ms_id` → `ban_ms_id_1`
  （原位改名，位置保持）。库侧走 `RENAME COLUMN` ⇒ 数据不搬。

## G.4 `AI_PARAM`：两个"假 gap"与三个"同构带块"

旧 schema 在 `csv19` / `csv22` 标了 gap，真实原因是 **列号游标 `v36` 按引用传给共享子读函数**：

```c
v36 = 18;
csv17 → +520 bit3
sub_56E890(a3+84, a1, &v36)                  // ★内部 (*a4)++ 5 次 ⇒ 吃 csv18..22
csv23..47  sub_56E220(&v34, v42, a1, &v36)   // ★内部吃 25 列 → 带 A（NEAR）
csv48      v42[0] = atof(csv48)              // ★带 A 独有的"块首 float"，不在子函数循环里
csv52..76  sub_56E220(…)                     // 带 B（MIDDLE），v42[0] = 0（不读 CSV）
csv79..103 sub_56E220(…)                     // 带 C（FAR），v42[0] = 0
csv122..125 sub_56E3F0(a3+504, a1, &v36)     // ★吃 4 列 → +504(u8)/+508/+512/+516
cssv126 → +521 bit0
```

- ⇒ 主函数里只看得到 `sub_56E890(&v36)` 这一句，**看不到游标前进**，于是静态扫描把 `csv19`/`csv22`
  误判成"没被读"。**仿真读集**（`_out_emu_readers.json`）给出的是连续的 `0..126` ⇒ 旧 gap 是假象。
- 三个带块**同构**：每块 25 列 = `{3 个 u8（atoi）, 22 个 float（atof）}`，块内 23 个 float 随后被
  `sub_56E450` **归一化（和 = 1）**。
- ★带 A/B/C ↔ `NEAR/MIDDLE/FAR` 的对应是**推定**：依据 `csv22` 枚举名（`sub_56E6B0`：`NEAR=2/MIDDLE=3/FAR=4`）
  与"带 A 独有块首 float、Mid/Far 该处为常量 0"的差异。**该推定已写入 schema 的 `columns_note`，属未取证项。**
- 旧注释里 `col18`/`col20`/`col21`/`col23`/`col24` 等"近/中距权重"的列位**全部错位**（把子函数内部偏移当列位），
  本批按展开后的游标逐列重排；`col42/43/44` 三个"整型/开关"也很靠后（真实位置在 `csv119..121/126`）。
