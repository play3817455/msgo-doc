### 16.2 `MSMA_COLORSET`：两句话修好（保留 64 行）

§12 已把 csv19 从 `region_gate` 订正为 `vip_gate`，**schema 是对的**，错的只是库（旧列没删、新列被 `ADD COLUMN` 追加到了末尾）。

关键：**不能**直接 `DROP region_gate` —— 那样 `extra_param_20` 和 `vip_gate` 会**互换位置**（物理顺序决定导出列序）。
正确解法是先删**末尾那个重复列**，再把旧名改成新名：

```sql
-- 安全闸：vip_gate 非空则拒绝（实测 0 行）
DO $$ ... IF n > 0 THEN RAISE EXCEPTION ... END $$;
ALTER TABLE cfg."MSMA_COLORSET" DROP COLUMN vip_gate;          -- 尾部空列（重复的那个）
ALTER TABLE cfg."MSMA_COLORSET" RENAME COLUMN region_gate TO vip_gate;
```

### 16.3 `MSMA_OVERWRITE_PARAMS`：把变长行显式落成 23 个物理列

**为什么必须扩**：本表行是 `<TYPE>,<REGION>,<ID>[,<FIELD>,<VALUE>]...`（变长），文档 78 一直写「不按列号建模」。
但 cfg 管线是**面向列**的，1 列建模把二义性夹在中间：

- 导入：`importCSVFile` 有 `len(colNames) < maxCol+1` 闸门 ⇒ 一行带 2 组对（7 字段）就会
  **整表导入失败**（不是丢一行，是 `cfgsync` 直接 `return error`）；
- 导出：`dataColumns()` 取 `information_schema` physical 顺序 ⇒ 列集与 schema 不符时导出列序会错。

于是"占位行能过、真数据永远回灌不了"。

**做法**：`tools/patch_overwrite_params_columns.py`（新增，可重跑）把列写成
`row_type, region, target_id` + `overwrite_field_1/value_1 … _10/_10` = **23 列**。
尾部未用的对**留空**；客户端对不认识的 FIELD 名**只 `++idx` 跳过它的 VALUE**（文档 78）⇒ 补齐空对安全，
且 23 = 3 + 20 是**偶数对**，不会让配对错位。⚠️ 超过 23 字段时**只能追加列**（append-only）。

### 16.4 ★顺带挖出一个导出层 bug（`ExportTableRawCSV` 表头粘连）

验证"可回灌"时用了一个临时 bootstrap 树（`_owtest/`，只放本表 CSV，**不碰仓库文件**）。
那些在临时树里**找不到 CSV** 的表会走兜底表头 `DefaultCSVHeader`，于是暴露出：

```go
// 旧代码（错）
b.WriteString(strings.TrimRight(headerText, "\r\n"))      // ← 先砍掉尾换行
if !strings.HasSuffix(headerText, "\n") && !strings.HasSuffix(headerText, "\r") { ... }
else if !strings.HasSuffix(headerText, "\r\n") { ... }    // ← 却拿**原串**判后缀
```

`DefaultCSVHeader` 返回的串以 `\r\n` 结尾 ⇒ `TrimRight` 砍掉了它，而两个后缀判断都基于**原串**

⇒ 客户端把**整行首数据当注释吞掉**（走兜底表头的表**每张白丢一行**）。

正常路径（`ExtractCSVHeader` 的返回值不带尾换行）不会触发，所以这个 bug 一直藏着。

**修法**：把表头拼接提成纯函数 `appendCSVHeader()`，判据落在 **TrimRight 之后**的串上，
并加 `csv_export_test.go` 锁死"表头与数据之间恰好一个 CRLF"（含事故形态 `\r\n` 结尾的兜底表头）。

**善后**：重跑 `cfgsync -bootstrap-csv ../server/datafiles/lounge` 把 76 张表的真实注释块全部还原，
复核 = **逐字节等于源文件的 `ExtractCSVHeader` 输出**、`row_count` 等于实际数据行数、0 处粘连 ✓

> 踩坑记录：临时树**不能**只放一部分 CSV —— 走不到文件就退化成兜底表头，而兜底表头又踩上面的 bug。
> 要局部导入就**先把目标表 TRUNCATE**（bootstrap 只灌空表），别用"裁剪过的 CSV 树"。

## 17. cfgsync 自检 + 定向重建（堵列漂移根因）· 2026-09-29

§16.6 #3 提的两件事本轮都做了：**漂移告警** + **`-recreate <table>`**。

### 17.1 判据：把「库列 vs schema 列」拆成三件事

新增 `serverv/internal/cfg/audit.go`，核心是**纯函数** `classifyDrift(want, got)`（不碰 DB，好测）：

| 差异 | 含义 | 会不会让导出错位 |
|---|---|---|
| `Extra` | 库里有、schema 没有 ⇒ **旧列残留**（改名的老列） | **会**（`ExportTableRawCSV` 按物理顺序取列 ⇒ 列序错） |
| `Reordered` | 集合相同但**顺序不同** | **会**（同上） |
| `Missing` | schema 有、库里没有 | 不会：下次 sync 的 `ADD COLUMN` 补到**末尾**，正好对上 schema 顺序 |

`ColumnDrift.Broken() = len(Extra)>0 || Reordered`。`SyncAll` 跑完自动 `AuditColumnDrift`，
只要有 `Broken` 的表就打印一行，并**把修法命令直接写出来**：

```
WARN 列漂移(导出会错位): <表>: schema N 列 / 库 M 列；**旧列残留 k 个** [...]；修法: cfgsync -bootstrap-csv <树> -recreate <表>
```

### 17.2 `-recreate A,B,C`：只重建点名的表

`SyncOptions.Recreate map[string]bool`（`cfg.ParseTableList` 解析逗号列表）。命中的表在
`ensureDataTable(..., drop=true)` 里 `DROP TABLE` ⇒ 建表为空 ⇒ 走 bootstrap 回灌（只灌空表那套逻辑不变），
**其他表一律不动**（这是相对 `-drop` 全局清的差别）。

`validateRecreate` 是**安全闸**，拒三种「删了补不回来」的目标：

1. schema 里没有的表名；
2. `SkipDB()` 的表（`AUTOEXEC` / `disposition=SCRIPT`）；
3. **磁盘上找不到 bootstrap CSV 的表** —— 本地表（`BGMPACKAGE` / `LVUP_MSMA` / `MSMA_MATERIAL`）
   就是这种：默认报错拒掉；确要重建（建库期可覆盖）时加 **`-force`** ⇒ 降级为「DROP + 建**空表**」并打印明确日志。
