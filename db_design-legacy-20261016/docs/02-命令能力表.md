# 02 · 命令能力表（受控标签）

> 上游：[`00-设计原则.md`](00-设计原则.md)（三层模型、`disposition`）、[`01-命令模型.md`](01-命令模型.md)（命令模型与状态阶梯）。
> 本文固化 `schema/commands/*.json` 的 `capabilities[]` 取值域，以及 `behavior[]` / `db_effects[]` 的生成口径。

## 1. 为什么需要「能力」这一层

命令维度上，字段讲的是**线上是什么**，行为讲的是**客户端/服务端做什么**，中间还缺一层可查询的分类：
「这条命令属于哪一类操作、作用在哪个域对象上」。这层分类用于：

* 数据库建模时按能力聚合（同一实体的 `query` 与 `update` 命令要一起看，否则会漏字段）；
* 服务器逻辑重排时按能力切分职责（哪些是纯查询、哪些会写库）；
* 站点上的筛选与矩阵页（`site/commands/capabilities.html`）直接按这些标签出表。

**纪律**：`capabilities[]` 的每个标签都必须能在该命令的汇编里找到落点（字段读取点/去向槽/日志串），
因此 schema 规定「**无汇编证据前必须为空数组**」——命令名推断的结果只能进 `capabilities_derived`。

## 2. 受控标签表

### 2.1 动词标签（一行一个，取命令名第一个命中的为主）

| 标签 | 含义 | 命名学正则（`_name` 小写后匹配） | 对应 `db_effects[].op` |
|---|---|---|---|
| `query` | 查：拉取/列举/回执查询 | `_get` `_list` `_search` `_info` `_select` `_check` `_query` `_find` `_load` `_read` | `read` |
| `create` | 增：新建/入场/购买实例 | `_create` `_add` `_new` `_post` `_entry` `_buy` `_gacha` `_make` `_regist` `_install` `_deploy` `_spawn` `_build` `_open` | `create` |
| `update` | 改：设置/编辑/装备/升级 | `_set` `_edit` `_update` `_store` `_change` `_apply` `_rename` `_unlock` `_equip` `_modify` `_use` `_upgrade` `_move` `_put` `_save` | `update` |
| `delete` | 删：丢弃/离开/踢出/取消 | `_del` `_delete` `_discard` `_leave` `_kick` `_refuse` `_cancel` `_remove` `_clear` `_disband` `_drop` `_unregist` | `delete` |
| `notify` | 推：广播/同步/回执 | `_notice` `_notify` `_broadcast` `_announce` `_sync` `_push` `_ack` | `read` |
| `settle` | 结算：战斗结算/奖励/排行/交易 | `_settle` `_result` `_reward` `_ranking` `_score` `_charge` `_pay` `_trade` `_exchange` `_deposit` `_withdraw` `_repair` `_heal` `_refuel` `_supply` | `update` |
| `validate` | 校验：登录/凭据/探测 | `_verify` `_validate` `_auth` `_login` `_probe` `_captcha` | `read` |
| `battle_action` | 战斗动作：攻击/伤害/开火/技能 | `_attack` `_damage` `_fire` `_weapon` `_skill` `_combat` `_battle` `_hp` `_respawn` `_snapshot` | `update` |
| `flow` | 流程：开始/结束/进出/初始化 | `_begin` `_end` `_start` `_stop` `_enter` `_exit` `_suspend` `_resume` `_ready` `_init` `_close` `_quit` `_join` | `update` |
| `report` | 上报：埋点/统计/日志类回执 | `_report` `_record` `_trace` `_stat` `_log` | `none` |
| `unclassified` | 命名学未命中（待批次复核时人工归类） | — | `none` |

> 一条命令可同时命中多个动词标签（如 `_result_info` 既 `settle` 又 `query`），
> 取前 3 个进 `capabilities[]`。**标签表是闭集**：新增标签必须同时改本表与
> `tools/derive_behavior.py` 的 `VERB_TAGS`，否则站点与校验会不一致。

### 2.2 域对象标签（`域.对象`）

格式 `<proto>.<对象>`：

* `<proto>` 取命令的 `proto` 字段（`auth` / `battle` / `lounge`）；
* `<对象>` 取命令名里**动词之前的连续标识符**（最多 2 段），例如
  `channel_list_get_r` → `lounge.channel`；`msma_adop_update` → `lounge.msma_adop`；
  `entity_deploy_arms_appear` → `battle.entity`。

作用：把「同一实体的一族命令」聚成一束，是 `db_effects` 反查与数据库建模的主要抓手。

## 3. `behavior[]` 生成口径

`behavior[]` 是**逐步骤的读写行为**，每一步都必须带汇编证据 VA。顺序固定为：

| 顺序 | `kind` | 何时出现 | 证据 VA 来源 |
|---|---|---|---|
| 1 | `read_scalar` / `write_scalar` | 恒有（opcode 行） | `extra.opcode_field_va` / `extra.opcode_write_va` |
| 2 | `alloc` | C→S 且有容量指纹 | `asm_verification.checks.capacity.va` |
| 3 | `guard` | S→C 且取到守卫 | `checks.field_window.guard.va` |
| 4 | `read_*` / `write_*` | 每个报文体字段一条（`seq ≥ 1`） | 字段自身 `evidence_va[0]` |
| 5 | `close_check` | S→C 且有闭合点 | `checks.closer.va` / `closer_va` |
| 5' | `commit` | C→S 且有提交点 | `checks.closer.va`（`kind=commit`） |
| 6 | `dispatch` / `send` | 有去向槽 | `checks.dispatch_slot.va` / `dispatch_va` |
| 7 | `error_path` | 有 `vt[0x64]` 报错槽 | `checks.dispatch_slot.error_slot.va` |
| 8 | `notify` | 有 `[obj+79A8h]` 附加通知 | `extra.notify_va` |

字段级 `kind` 的判定（`tools/derive_behavior.py:field_kind`）：

* 被某个 `structs[*].members[].count_field` 引用 → `read_count` / `write_count`（条数驱动）；
* `char[N]` / `str*` / `blob` → `read_string` / `write_string`；
* `array<...>` / `X[N]` → `read_array` / `write_array`；
* `struct<...>` / `composite` → `read_struct` / `write_struct`；
* 其余标量 → `read_scalar` / `write_scalar`。

## 4. `db_effects[]` 生成口径

**只认既有证据，不凭命名臆造**。来源两处：

1. `schema/tables/*.json` 的 `columns[].wire_sources[]`（带 `command` / `field_name` / `evidence_va`）；
2. `schema/entities/*.json` 的 `wire_forms[].commands[]`（表还没提议出来时的实体级证据）。

输出字段（schema 硬约束，`additionalProperties: false`）：
`{entity, table_ref, op, fields[], disposition, evidence_va}`。

* `op` 取该命令**首个动词标签**映射（见 §2.1），因为服务端对 DB 的动作方向由命令语义决定；
* `disposition` 直接沿用表列/实体的 `disposition`（`PERSIST` / `CONFIG` / `EVENT` …）；
* 无证据的命令 `db_effects = []` 且写 `db_effects_note` 说明原因，站点上显示为「无既有实体/表证据」。

## 5. 状态阶梯与门禁

| 状态 | 门禁 |
|---|---|
| `IMPORTED` | 从 `protocol_analysis` 导入；六项 check 有空项 |
| `ASM-VERIFIED` | 六项 check 全非空，且差异要么为空、要么全是 `--apply` 可闭合的记账差异 |
| `BEHAVIOR-DONE` | 已 `ASM-VERIFIED` **且** `behavior[]` 非空且每步有 VA **且** `capabilities[]` 非空 **且**（`db_effects[]` 非空 **或** 已写明 `db_effects_note`） |

`capabilities[]` 只在 `ASM-VERIFIED` 及以上才写；`behavior[]` / `db_effects[]` 全量先算，
等 IDA 批次复核把状态推上去后自动成为 `BEHAVIOR-DONE`。

## 6. 机械校验

```bash
python tools/derive_behavior.py --validate   # 严格校验 915 条（枚举/多余键/step 连续性/VA）
python tools/derive_behavior.py --summary    # 统计（不写文件）
python tools/derive_behavior.py --write      # 落库 + 刷新 index.json
```
