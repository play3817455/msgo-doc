# 00 · 数据库字段设计原则

> 产出日期：2026-09-20  
> **本阶段唯一证据源：`protocol_analysis/`（915 命令 DONE）**

---

## 1. 证据规则（硬约束）

| 允许 | 禁止 |
|---|---|
| `protocol_analysis/commands/<命令>/README.md` | `server/` 代码与迁移 |
| 同目录 `fields.csv` / `asm.md` / `notes.md` | `api_doc/` 旧文档 |
| `_meta/长期记忆.md` 中的**线宽/写入器**结论 | 任何「表已存在」「列已建好」的假设 |

JSON 里每条字段必须有 `wire_sources[]`，指向协议路径。  
**不得**写 `core.characters.xxx` 当作既成事实；表名只能是 **`proposed`（设计提议）**。

---

## 2. 三层模型

| 层 | 是什么 | 本目录 |
|---|---|---|
| **Wire 字段** | 协议线上的字段 | `schema/fields/index.json`（自动草稿） |
| **Canonical 实体** | 合并多种线宽后的业务字段 | `schema/entities/*.json` |
| **DB 列（提议）** | 应持久化的列 | `schema/tables/*.json` |

---

## 3. disposition 分类

| 值 | 含义 | 提议建列 |
|---|---|---|
| `PERSIST` | 应持久化 | ✅ |
| `DERIVED` | 编解码时从别处填入 | ❌ |
| `TRANSIENT` | 仅当次响应（如 `result`） | ❌ |
| `EVENT` | 战斗/会话 ephemeral | ❌ |
| `COMPOSITE` | 聚合体容器 | 看子段 |
| `CONFIG` | 静态配置表 | ❌ |
| `TBD` | 未决定 | 待定 |

---

## 4. 聚合体内部分段

`avatar(18B)` 等由写入器逐段写线（如 `sub_B06290` = `4+1+1+1+2+4+1+1+1+2`）。

- 线宽/偏移 → 必须来自 `protocol_analysis`（asm / README / 长期记忆）
- 成员**语义名** → 仅当 README §3.x 或打印器已取证；否则标 `TBD`
- 定义放在 `schema/composites/*.json`，表设计引用 `composite_ref`

---

## 5. 工作阶段

| 阶段 | 标志 |
|---|---|
| **P0 草稿** | `import_from_protocol.py` 产出，disposition 多为 TBD |
| **P1 提炼** | `tables/*.json` 有列 + wire_sources ← **当前** |
| **P1 单表补全** | `status: complete`；composite 无 TBD 成员；见 `schema/_meta/completion_queue.json` |
| **P2 定稿** | 全实体归类完成，可写 migration |

**补全规则**：一次只补一张表；补完（`completion_queue.json` 登记）后再开下一张。必要时用 IDA MCP 读打印器/读取器汇编取证。
